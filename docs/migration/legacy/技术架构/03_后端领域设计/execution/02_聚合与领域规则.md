## 1. 聚合与核心类图

`TrainingRecord / LearningRecord / SleepRecord / MealRecord` 是封闭类型的 ExecutionFact 聚合，使用统一稳定头与不可变修订协议，各专属内容是类型化模型，不能以万能 JSON 替代。一个事实当前指针只指向一版；某次纠正完整复制并替换该事实正文，旧版不重复累计。FoodAnalysisDraft 是独立聚合；事实不加载整个计划、结论或 AI 任务。

图中每份内容只允许匹配 kind 的一个专属对象；APPLIED 基准为引用，不可独立编辑；自主事实 refs 为空。FoodLine 在草案/事实分别具有独立不可变 lineId，确认时复制个人确认的值，后续草案编辑不能改已确认事实。

## 2. 状态与生命周期

```mermaid
stateDiagram-v2
    [*] --> NoFeedback
    NoFeedback --> COMPLETED : 本人保存
    NoFeedback --> PARTIAL : 本人保存
    NoFeedback --> NOT_PERFORMED : 明确未执行
    COMPLETED --> COMPLETED : 纠正形成新修订
    COMPLETED --> PARTIAL : 纠正形成新修订
    PARTIAL --> COMPLETED : 纠正形成新修订
    PARTIAL --> NOT_PERFORMED : 纠正形成新修订
    NOT_PERFORMED --> PARTIAL : 纠正形成新修订
    COMPLETED --> REMOVED : 误记删除
    PARTIAL --> REMOVED : 误记删除
    NOT_PERFORMED --> REMOVED : 误记删除
    REMOVED --> [*]
```

NoFeedback 是查询状态，无空事实占位；未来/休息/暂停来自 planning，不是事实状态。误记删除不能隐式恢复；睡眠独立 `IN_PROGRESS → COMPLETED → REMOVED`，IN_PROGRESS 只有已经发生的开始，不宣称完成或计完整时长。

```mermaid
stateDiagram-v2
    [*] --> EDITING
    EDITING --> ANALYZING : 创建当前输入任务
    ANALYZING --> NEEDS_CHECK : 接纳有效候选
    ANALYZING --> NEEDS_INFO : 不足或非食物
    ANALYZING --> FAILED : 调用失败
    ANALYZING --> EDITING : 输入修改使旧任务过期
    FAILED --> ANALYZING : 显式重试最新输入
    NEEDS_INFO --> EDITING : 补图或手动补充
    NEEDS_CHECK --> EDITING : 修改份量或来源
    EDITING --> NEEDS_CHECK : 人工核对完成
    NEEDS_CHECK --> CONFIRMED : 本人确认实际食用
    CONFIRMED --> [*]
```

需要重估的修改不能继续展示旧数值为最新；NEEDS_INFO 也可在本人明确确认未知项后转 NEEDS_CHECK。CONFIRMED 草案只读，重复确认返回同一 factId；摄入修正另建绑定原 factId/expectedFactVersion 的修正草案，确认后写原事实新修订。取消修正保持原入账内容。

## 3. 事实、日期与基准规则

1. `occurredAt` 必须已发生；睡眠完整 endAt 晚于 beginAt 且不晚于服务器当前时间。NOT_PERFORMED 对应已到时点项目，不把未来任务提前登记为失败。普通日期由事实实际时间校验；业务日期不能由今日页面强制覆盖。
2. 保存训练/学习/完整睡眠和摄入前同事务调用 planning.protectBaseline；有计划保留目标/项目修订，无计划 refs=[]。基准候选过期/冲突要刷新或明确选择自主路径，不静默选某目标。BLOCKED 是未来任务限制提示，不能拒绝本人如实记录。
3. 已有事实纠正使用 EXISTING_BASELINE，保留 originalProtectionId 和原 refs；改变日期保存原/新归属影响，不因新日当前计划而重新绑定。移日摄入同时保护新日总量槽，返回 supplementalProtectionId，旧槽不解锁；没有目标也冻结用户/日总量槽。新日多个冲突总基准须 supplementalDaySelectionRefs 明确选择；新日冻结总量不替换事实原基准。原基准日期不再匹配标 baselineDateMismatch，不给新日虚构达标率。
4. 多目标睡眠/摄入一个正文和 factId，查询按事实 ID 去重。冲突时 planning 的共享主基准选择须明确 PRIMARY/REFERENCE/EXCLUDED；不能各用一个矛盾目标并复制事实。自主事实之后不补造历史目标。
5. 睡眠 D 日属于 D−1 夜至 D 晨；周日夜到周一晨归下周。不根据 profile 常规作息补事实。START+SLEEP 接受已发生 beginAt、明确预计起床日、endAt=NULL、provisional=true，只保护已开始范围。完成后复用同事实和原开始保护，真实 endAt 决定归属；旧/新日 token 均变，原目标不匹配则标记而不自动换目标。进行中片段不计完整时长/结论。
6. 训练动作明细可选；无动作记录的 PARTIAL 30 分钟不推定7组完成。有动作时只保存本人输入的组次/秒/分钟/负重及单位，格式非负/正数不代表健康阈值。单次训练不适是 UNKNOWN/NONE/REPORTED 的本人报告，不自动变医学诊断或日级身体状态。
7. 学习一个计划项目反馈只有一个当前事实；多个片段以 fragmentId/fragmentKey 幂等追加或替换。分钟/页/题保留各自单位，缺失保持未知；成果文字可单独保存，不填0时长、不推算掌握率。不同单位不合成一个总量。

## 4. 摄入、换算和覆盖规则

每项 FoodLine 必有个人份量状态及四项营养知识状态。个人份量可明确 UNKNOWN 并保存已吃食物事实；数值未知保持 NULL，不据未经核对整盘给确定个人摄入。估算整盘全部吃完必须由用户明确确认估算依据；portionAssumption 仍标 ESTIMATED。

同餐多图经整个输入集合一次分析/核对，各 line 保存支持图片集合和合并状态；不以图片数加总。候选重叠而不能确定合并时返回待核对，不自动认定两份。不同餐次吃同类食物不是重复事实。草案 CONFIRMED 指针、事实来源草案唯一键、公用命令幂等共同防重复确认。

转换先保存原值/单位/每100g或每份/参考重量，再使用本人实际量：例如800kJ/100g、食50g → 400kJ → `95.602294... kcal`。内部 DECIMAL(18,6)，展示按渠道配置舍入并保留 conversionVersion，不把显示舍入值作为下次转换输入。份量及营养区间非负且上下界成对，乘非负比例分别换算上下界；缺关键依据变 UNKNOWN。宏量缺失不由热量反推。

已确认、当前 ACTIVE、occurredAt 不晚于 cutoff 的 MealRecord 参与小计，每事实只用当前一版。每营养项返回 `knownSubtotal`、已知范围小计、unknownItemCount、coverageState=COMPLETE/PARTIAL/UNKNOWN；含未知项时不是完整全天值，不能把已知下界当全天总量。空记录返回 `recordedCount=0、knownSubtotal=null、coverageState=NO_RECORDS`。明确输入0与未知NULL不同。只有 planning 当前可对照基准才有差额；无目标不给差额或达标率，超出保留方向与负差额，不截断、不安排补偿。

事实范围 token 为 FACT_DAY(userId,date,dimension)，维度 TRAINING/LEARNING/SLEEP/MEAL；新增、纠正、删除均同事务递增。跨日纠正各日各递增一次；影响训练信号还供 FITNESS 证据读取使用同一 TRAINING token。草案使用 FOOD_DRAFT(userId,draftId) token，仅任务最新性使用，不进入日结论事实源。

覆盖依据 planning 适用范围与 cutoff，返回 dueItemRefs、registeredItemRefs、missingItemRefs、excludedItems（FUTURE/REST/SUSPENDED）、自主事实数量、各状态数量和未知字段。没有事实不等于未执行；额外事实不替代原任务。Nutrition 的登记餐次覆盖与营养未知完整性分别表达，不能称“漏餐=0”。覆盖计算是查询，不生成每日空记录。
