Goal、WeekPlan、PlanReview 是独立仓储和生命周期。WeekPlan 装载一周的项目/当前草案及必要保护状态；不装载事实、图片、结论或全部历史。DailyIntakeGuard 是用户/日一致性保护对象，由 planning 仓储单独锁定，不能作为第二份摄入事实。Publication 是 WeekPlan 内不可变发布实体；FitnessPolicies 是纯规则，不访问数据库/供应商。

## 2. 目标状态与未来有效性

```mermaid
stateDiagram-v2
    [*] --> ACTIVE: 保存目标，可无计划
    ACTIVE --> PAUSED: 明确暂停未来范围
    ACTIVE --> ARCHIVED: 归档未来范围
    PAUSED --> PENDING_REPLAN: 请求恢复
    PENDING_REPLAN --> ACTIVE: 最新条件重新审查并确认未来范围
    PENDING_REPLAN --> PAUSED: 取消恢复或限制未解决
    PAUSED --> ARCHIVED: 归档
    PENDING_REPLAN --> ARCHIVED: 归档
    ARCHIVED --> [*]
```

状态历史带 effectiveAt 和项目影响集合，根当前状态用于新的规划资格；未来生效时点通过状态变更记录确定。暂停/归档不改已开始项目历史修订，已开始范围仍按原基准查询。只暂停选定风险项目时保持 Goal ACTIVE，生成项目级 SUSPENDED 发布操作；暂停整个目标时 Goal PAUSED。恢复目标进入 PENDING_REPLAN，旧暂停项目不会因根恢复就重新可执行，须逐项通过新发布恢复。归档的恢复不在 V1 范围，另建目标不复制历史事实。

目标修改形成新 GoalRevision；已有计划时类别不可换。计划基准引用当时 goalRevisionId，目标新名称、期限和衡量不改历史分母。目标修订、状态、条件变更均递增相关 scopeTokens，让未完成审查失效。

## 3. 草案、审查及发布状态

```mermaid
stateDiagram-v2
    [*] --> EDITING
    EDITING --> REVIEWING: 最新完整草案申请审查
    REVIEWING --> NEEDS_CHANGE: 阻断项
    REVIEWING --> INSUFFICIENT: 信息不足
    REVIEWING --> READY: 完整适用审查完成
    REVIEWING --> FAILED: AI失败或审查不可用
    READY --> PUBLISHED: 本人明确所选未来范围
    NEEDS_CHANGE --> EDITING: 修正内容生成新草案
    INSUFFICIENT --> EDITING: 补充条件或内容
    FAILED --> REVIEWING: 重试相同输入
    READY --> STALE: 草案或来源变更
    REVIEWING --> STALE: 输入变更
    STALE --> REVIEWING: 审查最新输入
    PUBLISHED --> EDITING: 编辑仍可调整未来范围
```

状态是当前草案与对应 PlanReview 的组合投影；不能直接修改草案状态来获得发布资格。工作版取舍为 channel=RULES/AI：RULES 由 planning 的版本化确定性策略检查结构、数据充分性、时段/共享基准冲突、发布保护和健身限制，保存完整 PlanReview、覆盖结果和规则版本；只有适用检查覆盖充分且无阻断/信息不足才 READY。缺方法/参数/规则覆盖返回 INFORMATION_REQUIRED 或 RULE_COVERAGE_INSUFFICIENT，保留草案/旧计划，不能由前端勾选通过。AI 是授权后额外语义审查，选择该渠道必须等待其最新结果，失败不能自动降级；本人可显式切换 RULES 对最新输入重审，不能绕过产品禁止项。切换渠道保留已识别禁止项及其来源，仍存在的禁止内容不能因为新渠道未报告就消失，须由当前批准策略重新验证解决。该取舍待正式评审/冻结，不代表实现完成。

审查输入指纹包含完整逐日内容（动作顺序、名称、组数、每组数量单位、休息）、目标修订/状态、条件、授权、规则、跨目标安排范围、保护状态、调整来源、refs/tokens。AI 结果返回时在用户栅栏内重算。修改任何动作形成新 DraftRevision，旧审查和意见处理不能继续授权。普通建议保留只写意见决策，不改草案；采纳/自定义改变内容则重新审查。

## 4. 稳定身份、部分发布与历史

1. `(userId, goalId, weekStartDate)` 唯一 WeekPlan；当前 DraftRevision 由根指针确定，历史不可变。周/日编辑同一根，expectedVersion 防止覆盖。
2. `(weekPlanId, businessDate, slotKey)` 唯一稳定项目；slotKey 由服务端分配，例如每日总量槽、单次训练槽、睡眠槽，不能以可编辑标题作身份。删除项目形成 REMOVE 修订；恢复同槽保留身份。改日期等同删除旧项目并新增项目，只能未来可调整范围。
3. Draft manifest 是全周项目修订组合，未涉及项目引用旧修订；不把周四动作覆盖到周二。ItemRevision 含完整适用明细，不在执行时拼接“最新动作”。
4. 发布请求显式 selectedItemIds 和预期原修订，原子切换这些项目的当前发布指针。Publication 保存所选变化、完整发布后周组合和审查依据。未选项目的当前指针不动。新修订可 UPSERT、REMOVE、SUSPEND、RESUME；历史发布不更新。
5. 已开始/已有实际保护不可被发布替换。发布不得静默跳过某项；返回受保护项目冲突，用户刷新差异缩小范围后重提。整周按钮仅是显式选择全部可调整范围，不引入第二套版本模型。
6. 指针查询按稳定项目当前发布组合；历史对照按 execution 的 itemRevisionId/goalRevisionId 和 publicationId 读取。按时间查看某次发布则读取 Publication manifest；不能拿最新 WeekPlan.version 替换过去。

## 5. 执行保护与个人共享基准

| 范围 | 保护规则 |
| --- | --- |
| TRAINING / LEARNING | 真实开始或保存完成/部分/明确未执行事实均冻结项目处方与当时目标修订；真实实际量独立保存。 |
| SLEEP | 按 wakeAt 的上海日期定位，beginAt 可能属于上一周；开始标记、已保存睡眠或时段历史边界均保护项目。周日调周一不能修改周日夜已开始睡眠。 |
| NUTRITION_TOTAL | 任意同日个人摄入首次确认后 user/date 槽锁定。冻结当时全部相关目标的总量修订及无目标状态；以后不得添加、删除、换成另一总量。 |
| MEAL | 保存该餐摄入/标记开始冻结餐次修订；当日未开始餐次可在总量不变、已保护餐次不变、全日分配仍一致的前提下调整。 |
| 自主事实 | 返回 refs=[]，不要求计划，也不要求 PlanReview；自主摄入仍创建 user/date 总量槽，防止事后补造今日目标。 |
| 纠正/误记删除 | 引用原不可变基准；事实可纠正、移日或删误记，但不自动解除已存在历史保护。改归属时保护旧、新范围，不换历史目标美化差异。 |

多个目标同时设置个人同日饮食总量/睡眠时，发布前选择主基准或明确复用相同处方的引用关系。冲突选择只影响用户明确选择的关联目标/项目，不静默移除其他目标；若解决冲突需改其他目标，分别编辑其草案并完成审查。保护时输入 selectedBaselineRefs，逐一核验归属与修订；冲突返回 BASELINE_SELECTION_REQUIRED。该选择不阻止用户保存自主事实，可显式选择无计划路径，事实总览仍一次。

## 6. 健身策略与字段规则

| 策略 | 输入与结果 | 不变量 |
| --- | --- | --- |
| WorkoutPrescriptionPolicy | 类型、有序动作、数量/单位/休息；字段级问题 | 力量/按组至少一项；名去空白非空；组数/次数正整数；秒/分钟数量正数；休息整数秒≥0；0表示连续；休息日不强制动作。 |
| PublishableRangePolicy | 当前时间、真实开始/实际保护、状态历史、selectedItems | 只能未来未开始无实际范围；过去不补造应执行项。无时段今日新项以确认时刻为 effectiveNotBefore，不产生此前分母。 |
| CrossGoalConflictPolicy | 用户日期范围所有目标的当前安排+草案变更 | 返回具体重叠/共享基准冲突；用户明确处理，不自动跨模块排程。 |
| FitnessRestrictionPolicy | 当前 profile、FitnessEvidenceReader 证据、目标/动作/影响日、已批准 ruleVersion | ALLOWED/WARN/BLOCKED/信息不足；禁止风险内容不可用确认绕过；明显不适限制增加强度并提示暂停；不按漏餐/单餐估算做极端补偿。 |
| NutritionTargetPolicy | approved methodVersion、个人适用输入、事实引用、units | 记录方法及参数证据；参数缺失返回 missingParameters，不猜年龄/活动/体重；无批准方法不生成个性化数值。 |
| MealAllocationPolicy | 每日总量、餐次、固定已开始餐次、待分配范围 | kcal/g 同单位；已知分配总和等于已知总量。部分未知返回未分配量/未知，不能称完整一致；各宏量与热量矛盾由批准规则判定。 |
| LearningPrescriptionPolicy | 主题、内容、时段、数量单位、预期成果 | 分钟/页/题等独立；文字成果允许无数量；不转换为掌握率，不强制健康字段。 |

计算流程是“检查方法批准/适用 → 取版本化参数证据 → 计算候选/范围 → 精度规则舍入 → 分配与合计校验 → 草案/审查”。生产公式、系数、精度容差及健康边界均为 TBD-001，不在本设计写死经验系数；保存 calculation snapshot 与 ruleVersion 支持后续审核。结构合法的有限手工目标可保存，依据不足是否可发布由适用健康规则决定，不能伪造审查通过。

FitnessRestrictionAssessment 不复制身体事实正文，保存最小证据引用/规则理由和影响项目；当前读取与最终发布在栅栏内重新评估，即使 BodyObservationChanged 未消费也不能放行旧风险安排。对真实事实的 protectBaseline 无增加强度门禁，只负责历史身份/版本一致性。
