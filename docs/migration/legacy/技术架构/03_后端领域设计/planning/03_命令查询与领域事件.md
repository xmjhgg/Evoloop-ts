## 1. HTTP 契约

所有路径以 `/api/v1/planning` 为前缀。actor 从服务端取得；所有写操作先 identity 用户栅栏再公共幂等。`expectedVersion` 是被修改根的版本，草案没有独立可变 version；draftRevisionId/draftNo 为不可变身份/序号。失败使用共同错误信封，不返回其他用户对象存在性。创建 201、查询/更新 200、异步任务 202。

| 方法 / 路径 | 输入 | 输出 / 核心错误 |
| --- | --- | --- |
| POST `/goals` | name、category、description?、measure?、startDate、expectedEndDate?、fitnessDirection? / learningTheme? | goalId、goalRevisionId、version=1、status；422 INVALID_GOAL / INVALID_PERIOD |
| PATCH `/goals/{goalId}` | expectedVersion、可编辑目标字段，不接收状态强改 | 新 goalRevisionId/version；409 VERSION_CONFLICT / CATEGORY_LOCKED |
| GET `/goals?category=&status=` | 类别、状态、分页 | 稳定目标及修订、状态有效时间、本周/下周入口；无计划不虚构 |
| GET `/goals/{goalId}/weeks/{weekStartDate}` | 周一日期 | weekPlanId?、version?、当前 draft、当前发布组合、日动作摘要和限制/保护 |
| POST `/goals/{goalId}/weeks/{weekStartDate}/draft` | expectedGoalVersion、source=MANUAL/COPY、copyPublicationId?、weekFocus? | 唯一 weekPlanId/currentDraftRevisionId/version；已存在返回现草案，COPY须显式后续编辑；409 SOURCE_STALE |
| PATCH `/weeks/{weekPlanId}/draft` | expectedVersion、baseDraftRevisionId、weekFocus?、itemPatches[] | draftRevisionId、draftNo、version、差异、reviewStatus=STALE/NOT_REVIEWED；422 INVALID_ITEM，details含日期/item/action/field |
| POST `/weeks/{weekPlanId}/generation-tasks` | expectedVersion、baseDraftRevisionId、selectedDateRange、constraints? | taskId、weekVersion、inputDraftRevisionId、status=QUEUED；403 PURPOSE_DENIED，422 INFORMATION_REQUIRED |
| POST `/weeks/{weekPlanId}/reviews` | expectedVersion、draftRevisionId、channel=RULES/AI | RULES同步201：reviewId/version、READY/NEEDS_CHANGE/INSUFFICIENT、ruleVersion/coverage；AI异步202：reviewId/version/taskId/REVIEWING；结构错误422，规则覆盖不足阻止发布 |
| GET `/plan-reviews/{reviewId}` | 无 | 原输入版本、当前latest、status、issues、来源不足/过期原因 |
| PUT `/plan-reviews/{reviewId}/issues/{issueId}/resolution` | expectedVersion=reviewVersion、decision=KEEP_ADVISORY、reason? | reviewVersion、issueResolution；采纳/自定义改内容走草案 PATCH，禁止将阻断项设已解决；422 ISSUE_CANNOT_BE_WAIVED |
| POST `/weeks/{weekPlanId}/publications` | expectedVersion、draftRevisionId、reviewId、expectedReviewVersion、selectedItems[{itemId,oldPublishedRevisionId?}]、sharedBaselineSelection?、expectedAuthorizationVersion | publicationId/no、weekVersion、changedItems、新完整 publishedManifest、confirmedAt；409 REVIEW_STALE / SOURCE_STALE / ITEM_PROTECTED / BASELINE_SELECTION_REQUIRED；422 PUBLISH_BLOCKED |
| POST `/weeks/{weekPlanId}/adjustments` | expectedVersion、draftRevisionId、basisRefs、cutoff、patches、conflictSelections | currentDraftRevisionId/version、mergeStatus、conflicts、未发布；409 BASIS_STALE / MERGE_BASE_CHANGED / ITEM_PROTECTED |
| POST `/goals/{goalId}/pause` | expectedVersion、effectiveAt、scope=ALL_FUTURE/ITEMS、itemIds?、reason? | goalVersion、status、suspendedItems、preservedItems；409 ITEM_PROTECTED（若请求要求改保护项则整体拒绝） |
| POST `/goals/{goalId}/resume` | expectedVersion、effectiveAt、requestedDateRange | status=PENDING_REPLAN、goalVersion、planningScope，未重新启用旧计划 |
| POST `/goals/{goalId}/archive` | expectedVersion、effectiveAt、reason? | goalVersion、status=ARCHIVED、未来停止范围、历史引用保留 |
| GET `/baselines?goalId=&from=&to=&revisionId=` | 日期范围、可选历史修订 | 按项目不可变基准、适用目标修订、保护、共享选择，不汇总实际 |
| POST `/fitness-restrictions/evaluation` | goalId、影响日期/项目、ruleVersion? | assessmentId、ALLOWED/WARN/BLOCKED、ruleVersion、reasons、refs/tokens、missingEvidence；评估记录若落库遵约短写 |
| GET `/weeks/{weekPlanId}/publications/{publicationId}` | 无 | 当次选择差异+完整周发布组合+审查/来源引用 |

RULES 为工作版确定性适用审查渠道，检查结构、数据充分性、时段/共享基准冲突、保护与健身限制，规则覆盖充分才 READY；不等于用户手工勾选完成。AI 为额外语义审查渠道，失败不自动降级，用户可显式选择 RULES 对最新输入重新创建审查。缺批准健康参数、方法或检查覆盖时返回 INFORMATION_REQUIRED/RULE_COVERAGE_INSUFFICIENT；所有路径仍受禁止项门禁。此取舍待正式评审，未声称渠道已实现。

## 2. PlanningApi 公开契约

### 2.1 getBaselines

`getBaselines(actor, goalIds?, dateRange, historicalRefs?) → BaselineCollection`，只读，公开DTO不得泄漏实体。当前查询返回 `referenceGoalId, goalRevisionId, itemOwnerGoalId, weekPlanId, itemId, itemRevisionId, publicationId, businessDate, kind, effectiveState, startAt/endAt/effectiveNotBefore, quantity/unit, typedPrescription, protection, sharedSelectionVersion`。historicalRefs 指定既有 itemRevisionId 时校验本人归属后返回当时内容；不会回到当前修订。没有计划返回空集合和 scopeTokens。

typedPrescription 分别是 TrainingPrescription（动作完整有序）、LearningPrescription、NutritionTotalPrescription、MealPrescription、SleepPrescription，不用含混 payload 代替专属契约。睡眠既返回归属起床日，也返回前夜开始时间；数量与未知明确。

### 2.2 protectBaseline

`protectBaseline(actor, ProtectBaselineRequest) → PlanBaselineSnapshot`，**MANDATORY 调用方本地事务，禁止 REQUIRES_NEW**。execution 先分配事实 ID；输入为 `factId, factKind, requestId, businessDate, occurredAt, beginAt?, endAt?, provisional=false, mode=START/NEW_FACT/EXISTING_BASELINE, candidateRefs[], selectedBaselineRefs[], existingProtectionId?`。业务日期由实际时间按对应事实规则校验，完整 sleep 以 endAt 起床日期；EXISTING_BASELINE 用于纠正并引用原修订，不允许重选新计划。

START + SLEEP 的特定分支允许 endAt 为空，beginAt 已实际发生，businessDate 为用户明确的预计起床日、provisional=true；不能伪造完整起床或时长。完成时同 factId 以真实 endAt 更新归属，保留原开始保护并递增旧/新日期来源范围。预计日与真实日不一致时标明 baselineDateMismatch，原目标引用不自动换为另一日目标，进行中不计完整睡眠覆盖。

输出 `protectionId, factId, factKind, businessDate, lockedScope, baselineRefs[], sourceTokens`。baselineRefs 为上述不可变处方与目标版本；shared 主基准可重复被不同 referenceGoalId 引用，itemOwnerGoalId 标明真正项目归属。refs=[] 表示自主记录，禁止补造基准。MEAL 即使 refs=[] 也返回 `lockedScope=USER_DATE_NUTRITION_TOTAL`。

纠正 MEAL 的归属日时，EXISTING_BASELINE 保留原 baselineRefs/保护，不重选计划；同事务为新 businessDate 建立或核验用户/日摄入保护槽，按新日当时适用总量或明确无目标冻结，返回 supplementalProtectionId。旧槽不解除；新日冻结范围不是自动替换事实基准。事实保存原 protectionId 与新增保护引用；原基准日期不再匹配则标明 baselineDateMismatch，不能套成新日达标率。新增保护行引用 priorProtectionId，同 factId、requestId 幂等。

新日期尚无保护槽且有冲突总量时，输入另带 supplementalDaySelectionRefs 的明确主基准/引用选择；缺失则 BASELINE_SELECTION_REQUIRED，不自动挑一目标。补充选择只用于新日保护，原事实引用仍不变。

处理：栅栏已持有或首次取得 → 本人/授权核验 → Goal/WeekPlan/项目按ID锁定 → 验证候选适用修订/归属/选择 → 建立/保留项目保护 → MEAL 创建每日槽并冻结当时总量集合 → 保存不可变保护引用 → 返回 execution。execution 同事务写事实/修订/公共幂等结果和事件；任何一步失败全部回滚。相同 requestId+摘要返回同一保护，不增加新冻结；公共幂等由最外层事实用例持有，protect 不再创建另一个 sys_command_receipt。

错误：404 BASELINE_NOT_FOUND；409 BASELINE_STALE、BASELINE_SELECTION_REQUIRED、PROTECTION_CONFLICT；422 DATE_MISMATCH。**不返回 PUBLISH_BLOCKED 拒绝已发生事实**。当前限制随快照返回提示，但不能阻止真实反馈。无计划路径明确由用户选择，不能因冲突而偷偷关联任意计划。删除误记不自动解除保护。

### 2.3 evaluateFitnessRestrictions

输入 `actor, goalId, itemRefs/proposedItems, affectedDateRange, evidenceRefs?, expectedRuleVersion?`，输出 `assessmentId?, decision, ruleVersion, reasons[{code,severity,itemId,date,fieldPath,message}], missingEvidence, verifiedRefs, scopeTokens, evaluatedAt`。限制评估即时读取 profile 和 FitnessEvidenceReader，调用者传 evidenceRefs 仅作追溯期望，不当作可信当前事实。规则变更返回 RULE_VERSION_CHANGED；缺关键适用资料为 INFORMATION_REQUIRED，不猜数值。普通查询可返回提示；发布的权威评估须在已持栅栏短事务内重新运行。

`FitnessEvidenceReader.readEvidence(actor, goalId, dateRange, cutoff, kinds) → FitnessEvidenceSnapshot{evidence:[factId,revisionId,businessDate,occurredAt,kind,reportedDiscomfort/explicitRestrictionSignal], refs,scopeTokens}`，execution 实现，只读、无 planning 回调，不返回图片和不必要完整训练内容。同一事实多目标引用按 factId 去重。

### 2.4 mergeAdjustment 与来源倒置端口

输入 `actor, goalId, weekStartDate, expectedVersion, baseDraftRevisionId?, basisRefs[], cutoff, patches[], conflictSelections[]`。basisRef 含 `ownerModule=review, conclusionKind, conclusionId, revisionId, confirmationId/confirmationVersion, sourceRefs,scopeTokens`；patch 含 `patchId, itemId/clientItemKey, fieldPath, oldValue,newValue,affectedDate,reason`。输出 `weekPlanId, version, draftRevisionId, mergeStatus=MERGED/CONFLICTS_PENDING, conflicts[{patchId,currentValue,proposedValue,reason}], rejectedItems`；保存只产生草案。

`AdjustmentBasisVerifier.verify(actor,basisRefs,cutoff,affectedScope) → BasisVerification{latest, invalidReasons,verifiedSourceSet,verifiedConfirmations}`。review 在调用时检查结论身份、修订、人工内容、确认、覆盖/截止，以及底层 planning/profile/execution 的范围版本。端口接口归 planning.api；实现归 review；bootstrap 装配。实现不修改源域、不再次调用 mergeAdjustment/发布。

三方合并比较 patch.oldValue、当前草案值、newValue。原值匹配则写；不匹配且 proposed=current 视幂等；其他建立未解决冲突，用户 KEEP_CURRENT / USE_PROPOSED / CUSTOM 逐字段选择。冲突可以保存候选清单，但当前有效草案值保持；CONFLICTS_PENDING 不能发布。basis失效拒绝本次合并，不将历史理由当最新依据；普通独立手工编辑不要求复盘。跨周 patch 按受影响日期定位唯一 WeekPlan，HTTP 单次只接受一归属周；review 将跨周候选拆为多个显式合并命令。

### 2.5 getSourceTokens

`getSourceTokens(actor,goalIds?,dateRange) → SourceReferenceSet` 返回现有目标/项目修订及范围token。范围为 `GOAL_SET(userId)`、`GOAL_STATE(userId,goalId)`、`PLAN_DAY(userId,businessDate)`、`PLAN_GOAL_WEEK(userId,goalId,weekStartDate)`、`FITNESS_RULES(ruleScope)`。PLAN_DAY 覆盖同日所有目标适用安排、开始/实际保护、饮食总量槽和共享基准选择；新建目标/计划、暂停恢复、发布删除/替换也递增，不能仅返回现有 refs。用户范围首次不存在逻辑版本0；数据清理、移日改旧新范围。FITNESS_RULES取全局规则选择行scopeVersion，最终核验按04共享锁保护；不能用单用户scope行代替。授权版本/deletionEpoch 单独比较。

这里的“计划范围”是**已发布/适用处方及保护**，不是 WeekPlan 技术根所有写入。仅创建/编辑/合并草案、关联任务、更新审查/意见/需复核投影不递增 PLAN_DAY / PLAN_GOAL_WEEK；草案最新性由 draftRevisionId、输入指纹和目标 expectedVersion 检查。读执行结论来源不引用仅因草案更新而变化的 WeekPlan.version，使用适用 itemRevisionId/publicationId + 上述范围 token。否则“依据确认→合并草案”会使自己的依据立即过期，最终发布永远无法通过。发布/真实保护/暂停适用状态等实际变化才更新相应适用范围；审查所用其他工作草案直接绑定其 draftRevisionId，不伪装成适用计划token。

## 3. 核心工作流程

### 3.1 草案 → 审查 → 发布

```mermaid
sequenceDiagram
    actor User as 本人
    participant P as planning
    participant I as identity
    participant F as profile及证据端口
    participant A as ai
    User->>P: 保存完整逐日草案 expectedVersion
    P->>I: lockProcessingFence
    P->>P: 校验字段，新增不可变草案，旧审查失效，提交
    User->>P: 申请最新草案审查
    P->>I: lockProcessingFence + 授权版本
    P->>F: 当前条件/证据和范围token
    P->>P: 本地规则，锁定输入指纹与版本
    alt RULES 渠道
        P->>P: 确定性适用审查与规则覆盖，保存PlanReview，提交
    else AI 渠道
        P->>A: createTask，持久输入快照，提交
        A-->>P: AiTaskCompleted 候选结果
        P->>I: 新短事务 lockProcessingFence
        P->>F: 重读来源token
        P->>P: 共享锁当前规则选择，匹配才接纳，否则 REJECTED_STALE
        P->>A: recordAcceptance
    end
    User->>P: 明确确认 selectedItems + reviewVersion
    P->>I: lockProcessingFence
    P->>F: 当前条件/限制证据
    P->>P: 目标状态、草案、审查/意见、授权、规则、来源、保护再核验
    P->>P: 原子切所选项目指针，保存完整发布manifest和事件，提交
    P-->>User: 新 publicationId 和完整适用组合
```

最终核验在一个栅栏内完成，检查不能发生在事务外“先检查再写”；适用全局规则选择行 FOR SHARE 持有至提交，规则切换仅独占选择行且不申请用户栅栏，见04。每个新事务均先BEGIN再lockProcessingFence，序列图省略重复BEGIN。调整来源存在时，此处再调用 verify；旧审查即使事件未消费也拒绝。增加强度/极端补偿阻断不能 KEEP_ADVISORY 绕过。生成/审查失败仅更新任务/审查状态，不改原生效计划。

### 3.2 基准保护与事实保存

```mermaid
sequenceDiagram
    actor User as 本人
    participant E as execution
    participant I as identity
    participant P as planning
    participant DB as 同一MySQL事务
    User->>E: 保存真实实际或确认个人摄入
    E->>DB: 开启短业务事务
    E->>I: lockProcessingFence
    E->>DB: 校验公共幂等
    E->>P: protectBaseline 候选修订和真实发生时间
    P->>DB: 按Goal/WeekPlan/项目顺序锁定
    P->>DB: 保护当时修订，摄入保护用户/日总量槽
    P-->>E: 不可变PlanBaselineSnapshot
    E->>DB: 写事实/修订/基准引用/幂等结果/事件
    DB-->>User: 一次提交成功
    Note over P,DB: 保存失败则保护也回滚；保护不使用独立事务
```

发布也锁同稳定项目，用户栅栏将发布与事实写串行。若发布先成功，执行候选旧修订返回 BASELINE_STALE 让用户重核；若事实先成功，发布返回 ITEM_PROTECTED。周一睡眠的 beginAt 在周日，保护取真实开始时间，不看“下周”标签。风险限制只给提示，已发生事实保存保留。

### 3.3 调整合并与暂停恢复

```mermaid
sequenceDiagram
    actor User as 本人
    participant R as review
    participant P as planning
    participant I as identity
    participant V as AdjustmentBasisVerifier
    User->>R: 基于最新已确认结论调整未来
    R->>P: mergeAdjustment 同周patches和basisRefs
    P->>I: lockProcessingFence
    P->>V: verify结论、确认及底层范围版本
    V-->>P: latest / invalidReasons
    P->>P: 三方合并，只写明确选择，保留未涉及项目
    P-->>User: 草案或逐项冲突，尚未发布
    User->>P: 处理冲突，重新审查，明确确认
    P->>V: 发布前再verify
    P-->>User: 仅未来未开始范围生效
```

暂停先栅栏、幂等、锁目标和受影响周/项目，检查未来范围，形成状态历史与 SUSPEND manifest；已开始项目列入保留摘要，用户若明确请求修改它则拒绝，不能静默扩展/缩小范围。目标/范围 token 立即变化，AI在途接纳拒绝。恢复先核验最新条件、进入 PENDING_REPLAN，返回未来日期入口；重新安排/审查/发布原子使目标 ACTIVE 并仅 RESUME 选定项目。未确认新计划仍显示待规划/暂停，暂停期间不计缺勤。归档流程类似停止未来范围，不删除历史。

## 4. 事件与订阅

使用共同集成信封和单一持久事件登记；下表 payload 只含必要ID/状态/版本，不传播完整健康资料。消费以 `(consumer,eventId)` 去重，乱序按 aggregateVersion/scopeVersion 防回退；消费更改业务状态也先用户栅栏。

| 事件 | 发出时点 / payload | 订阅者及效果 |
| --- | --- | --- |
| GoalChanged | 内容修订或状态变化；goalId/revisionId/status/effectiveAt/affectedScopes | review 判来源过期；ai发起域拒绝旧输入；workspace刷新 |
| PlanDraftChanged | 草案编辑/生成接纳/合并；weekPlanId/draftRevisionId/version/changedItemIds | planning审查投影失效；workspace刷新，不触发实际累计 |
| PlanConfirmed | 明确发布；publicationId、selectedItemIds/revisionIds、affectedScopes | review 更新适用来源；execution刷新查询，不复制事实 |
| PlanItemLocked | 开始/实际/日总量保护；protectionId、itemRefs、锁定范围、时间 | review更新范围最新性；workspace显示保护；不当作新增事实 |
| FitnessRestrictionChanged | 当前限制评估变化；assessmentId、规则/证据版本、影响项目、decision | workspace提示、review核验依据；不会写execution事实 |

| 订阅外域事件 | planning 行为 |
| --- | --- |
| ProfileConditionsChanged / BodyObservationChanged | 将相关审查/评估投影标需复核；保留生效历史。最终校验仍即时读取当前来源。 |
| AuthorizationChanged / AccountStatusChanged / DataRequestCreated | 停止不适用接纳/生成，处理本域清理/导出回执，不直接修改其他领域。 |
| AiTaskCompleted / Failed / Cancelled | 校验ownerModule/taskKind/业务输入版本，接纳或标失败；业务接纳与任务调用成功分开。 |

## 5. 错误、重试和数据处理

客户端收到未知结果先查公共请求回执或目标当前版本再使用同一 Idempotency-Key 重试。409 幂等同键异输入不自动改请求；数据库瞬态失败有限同键重试；业务冲突必须刷新处理。task callback 用 eventId 去重及 taskId+review/draft 输入做业务接纳幂等，过期结果记录 REJECTED_STALE，不能覆盖新草案。

planning 不直接订阅 execution/review 类型事件，避免反向编译依赖。公开 `notifyFitnessEvidenceChanged(actor/受限模块上下文,eventId,sourceRefs,scopeTokens,affectedScopes)` 与 `markAdjustmentBasisChanged(actor/受限模块上下文,eventId,basisRefs,scopeTokens,affectedScopes)`：由 execution/review 自己消费其事件后，在新短事务先用户栅栏再 planning 锁调用，不能持源域事实/结论写锁回调。返回处理版本/ALREADY_APPLIED，按 eventId 去重、版本不回退；只更新需复核投影/其技术版本，不递增适用计划范围token，不发布、不写事实，最终 readEvidence/verify 权威核验仍执行。BEGIN→栅栏→幂等/消费去重→planning锁→提交为调用顺序。

后台合法业务接纳使用 BACKGROUND_TASK 并核验当前授权；取消、拒绝、租约释放、无正文失败元数据和清理使用受限 BACKGROUND_MAINTENANCE/FencePermit，不能借维护上下文发布或恢复正文。

导出/删除由 identity 事件受理：本域在持栅栏小批次读取/清理所有目标、修订、审查、基准保护、计算/限制快照、共享选择和范围token；清理期间不能接纳旧任务。历史引用被删除后其他域只能显示来源已删除，不重建。通过 IdentityApi.reportDataRequestStage 报告真实阶段，归档不能充当删除。
