## 2. 总体划分与业务闭环

系统划分为三个核心领域、一个个人条件支撑领域、一个账户通用领域和一个 AI 支撑能力模块。领域边界依据业务语义、状态变化规则和数据所有权确定，与页面入口、数据库表或部署服务不一一对应。

| 模块 | 业务名称 | 类型 | 回答的主要问题 | 主要模型候选 |
| --- | --- | --- | --- | --- |
| `identity` | 账户、授权与数据请求 | 通用域 | 谁在操作，允许处理哪些数据，数据请求完成到哪一步 | UserAccount、AuthorizationGrant、DataRequest |
| `profile` | 个人条件与身体观测 | 支撑域 | 当前具备什么条件，身体测量与日级身体状态是什么 | PersonalProfile、BodyMeasurement、DailyBodyState |
| `planning` | 目标与计划 | 核心域 | 希望达成什么，准备如何行动，哪个安排版本适用 | Goal、WeekPlan、PlanReview；健身限制模型待细化 |
| `execution` | 真实执行与个人摄入 | 核心域 | 实际发生了什么，哪些事实已由用户保存或确认 | TrainingRecord、MealRecord、SleepRecord、LearningRecord、FoodAnalysisDraft |
| `review` | 共享日结论与目标周复盘 | 核心域 | 如何理解计划与实际差异，用户认可了哪些判断 | DailyConclusion、GoalWeeklyReview |
| `ai` | AI 任务与模型接入 | 支撑能力模块 | 如何可靠完成生成、审查、图片理解与分析任务 | AiTask，含 InputSnapshot、TaskAttempt |

下图表示业务信息流转，箭头不是代码依赖，也不表示自动发布计划。

```mermaid

    F["profile<br/>个人条件与身体观测"] -->|条件版本| P
    F -->|身体事实| R
    subgraph CORE["核心业务闭环"]
        P["planning<br/>目标 / 草案 / 审查 / 发布"] -->|适用计划基准| E["execution<br/>训练 / 摄入 / 睡眠 / 学习事实"]
        P -->|目标与计划版本| R["review<br/>日结论 / 目标周复盘"]
        E -->|事实与修正版本| R
        R -->|已确认依据与调整候选| P
    end
    I["identity<br/>账户 / 授权 / 数据请求"] -.->|访问与处理资格| P
    I -.->|访问与处理资格| E
    I -.->|访问与处理资格| R
```

主闭环为：建立分类目标 → 编辑周每日草案 → 审查并确认计划 → 保存真实反馈 → 更新日结论 → 人工补充确认 → 目标周复盘 → 主动提出未来差异 → 回到同一周计划工作草案。用户也可自主记录或独立安排下一周，不要求先完成整条路径。

## 3. 统一语言与确认语义

| 术语 | 含义与所有者 | 需要区分的概念 |
| --- | --- | --- |
| 个人条件 | `profile` 保存的常规作息、可用时间、器材、基础与长期限制 | 可用时间是规划依据；计划时段是具体安排 |
| 身体观测 | `profile` 保存的带时间的测量或日级主观身体状态 | 最新资料引用观测；不覆盖历史测量，也不作医学诊断 |
| 分类目标 | `planning` 保存的稳定目标身份、类别、衡量、周期与状态 | 目标体重与实际测得体重分别归 planning、profile |
| 工作草案 | `planning` 中同一用户、目标、周的当前可编辑安排 | 草案保存与计划生效是两个状态变化 |
| 计划审查 | `planning` 对最新草案及其依据的检查、意见处理与发布条件 | 与 `review` 的执行后复盘使用不同对象和生命周期 |
| 真实事实 | `execution` 或 `profile` 唯一保存的用户记录，带归属时间和修正版本 | AI 候选、缺失信息、推测原因不能直接变成事实 |
| 适用计划基准 | `planning` 提供的执行时适用项目与不可变修订引用 | 事实引用历史基准，不用最新计划覆盖历史对照 |
| 日结论 | `review` 中每人每归属日一个对象，含目标分段和日总览 | 今日卡片与复盘页展示同一结论 |
| 目标周复盘 | `review` 中每人每目标每周一个对象，引用日结论与底层事实 | 周确认不代替每日确认，各指标保留各自含义 |
| 调整候选 | 由 `review` 的已确认判断支持的原值、新值、理由与影响日期 | 候选合并及计划草案版本由 `planning` 管理 |
| 业务接纳 | 业务所有者核验权限、来源版本、结果结构和业务规则后保存候选结果 | AI 调用成功仅表示任务执行结果，不代表接纳、确认或发布 |

| 用户动作 | 负责领域 | 生效语义 |
| --- | --- | --- |
| 保存执行或身体反馈 | execution / profile | 事实保存成功即成立，后续 AI 失败不回滚事实 |
| 确认个人实际摄入 | execution | 核对个人实际食用份量后形成摄入事实并参与汇总 |
| 保存计划草案 | planning | 保存待审查安排，原生效计划继续适用 |
| 保存人工结论补充 | review | 保存用户内容，影响判断时使旧确认需更新 |
| 确认日或周结论 | review | 认可最新来源、覆盖和截至时间内的判断 |
| 确认计划 | planning | 最新审查及依据有效时，仅发布明确选择的未来可调整范围 |

确认结论不能将任务登记为全部完成，也不能发布未来计划；目标归档不能代替隐私删除。以上对应 BR-COM-009、012～014、016～017。

## 4. 各领域职责边界

### 4.1 identity：账户、授权与数据请求

- **拥有**：微信身份关联、密码身份、本人会话、账户状态、按用途的授权及版本、导出/删除/注销请求和阶段回执。
- **主要行为**：微信/密码登录与会话恢复、管理员预建及重置密码、撤销会话、修改用途授权、创建数据请求、汇总处理进度。
- **协作**：向其他模块提供本人身份与授权查询；通过公开事件通知数据所有者，按公开回执契约收集结果。各域执行自己的数据处理，identity 跟踪真实完成状态。
- **不变量**：客户端 userId 不能授予访问权；撤回后限制相关处理；第三方或备份阶段未完成时如实呈现。AI 调用前、返回接纳与写入阶段均核验适用授权、账户及删除状态。

密码账号作为长期认证方式归 identity。当前一个账户最多一个密码身份，管理员脚本新建独立账户，不伪造微信关联、不按用户名合并账户、不开放注册/找回密码或身份绑定。密码重置撤销全部有效会话，不改变健康用途授权。浏览器访问密码属于部署网关，不形成业务领域身份；详情见[identity 设计](identity/README.md)。

### 4.2 profile：个人条件与身体观测

- **拥有**：常规作息、可用时间、器材、健身/学习基础、资源和长期限制的版本；身体测量与日级疲劳、精神、不适等身体状态事实。
- **主要行为**：保存个人条件，登记、补记、纠正测量或日级身体状态，提供条件及观测快照。
- **协作**：planning 读取相关条件作规划及限制判断；review 读取身体事实作复盘；我的和今日通过同一公开命令保存同一事实。
- **不变量**：测量保留实际时间、单位和修正历史；资料引用最新测量，不再保存另一份事实；学习条件不强制健康字段。条件变化使相关草案需复核，已生效安排按独立确认流程调整。

`DailyBodyState` 是日级身体状态的模型候选，用于承接 UC-FIT-011。某次训练后的感受保存在 execution 的 TrainingRecord；长期伤病或适用限制保存在个人条件。三者按语义分别记录，需要共享时引用来源事实，不通过复制变成不同版本的同一事实。

### 4.3 planning：目标与计划

- **拥有**：分类目标及状态版本、同目标同周工作草案、每日项目、训练动作、学习任务、饮食与睡眠安排、计划审查、发布修订及已开始/已有实际的保护状态。
- **主要行为**：创建修改目标、编辑逐日安排、合并调整候选、审查并处理意见、确认计划、锁定执行基准、暂停恢复归档目标。
- **协作**：引用 profile 条件和观测；请求 ai 生成或审查；向 execution 提供基准与锁定命令；接收 review 提供的已确认来源和候选差异。
- **不变量**：同用户/目标/周仅一个当前工作草案；每日项目仅一个当前生效修订；修改动作或相关依据使旧审查及处理状态失效；已开始或已有实际的范围受保护。恢复目标先重新规划、审查确认未来范围。

Goal 与 WeekPlan 是分别具有身份和生命周期的聚合候选。目标可先存在而没有周计划；WeekPlan 不装载执行事实、结论或图片。V1 在一个上下文内协调目标状态与未来安排。

健身个性化适用性、饮食目标计算、餐次分配、计划发布和调整的健身限制规则归本域健身能力。规则评估以版本化策略实现，并提供公开评估/限制查询能力供 execution、review 和 workspace 使用；具体规则参数和限制状态模型在详细设计中落实。

### 4.4 execution：真实执行与个人摄入

- **拥有**：训练、睡眠、饮食、学习的真实事实及修正历史；一次训练的感受；食物照片的业务关联、分析草案与个人份量确认。
- **主要行为**：登记补记纠正实际、分析食物、修改候选食物明细、确认个人摄入、删除误记、查询事实及覆盖情况。
- **协作**：有计划记录通过 planning 公开接口获取并保护适用基准；食物图片理解通过 ai 任务；营养成分数据通过本域外部端口获取；事实变更通知 review。
- **不变量**：完成、部分、明确未执行与未登记分别表达；无计划仍可自主记录；计划组数不自动转为实际完成组数。食物草案不入账，同餐多图不重复累计，按个人实际份量计算，未知值保留未知。睡眠按起床日归属，同一事实跨目标按引用复用。

营养数据供应商适配、标签单位/份量换算、已确认摄入小计属于本域饮食能力。AI 识别值、数据库来源值和用户标签输入保留来源、单位、范围与未知项；不因来源接入而建立自建食物库领域。

### 4.5 review：共享日结论与目标周复盘

- **拥有**：每人每日共享结论、目标分段和日总览；每目标每周复盘；人工补充、确认范围、覆盖、截至时间与来源版本集合。
- **主要行为**：生成更新日/周结论、保存人工判断、确认最新结论、识别来源过期、基于最新已确认判断发起未来调整。
- **协作**：读取 planning、execution、profile 的公开快照并请求 ai；向 planning 提交来源和候选差异，提供调整依据核验实现。
- **不变量**：事实、估算、未知与原因推测分别表达；人工信息保留；事实或补充变化使相关确认与派生依据需更新。有限记录可形成有限结论，覆盖与截止明确；周确认不代确认每日；结论确认不发布计划。

本域负责调整的判断依据与建议表达，planning 负责合并后草案、冲突选择、未来范围和最终发布。提出调整及发布前均核验结论和底层来源仍最新，普通手工规划可独立进行。

### 4.6 ai：AI 任务与模型接入

- **拥有**：持久任务、输入快照、模型/提示版本、调用尝试、租约、失败重试与业务接纳回执。
- **主要行为**：创建、领取、执行、重试、取消任务，适配文本模型和图片理解，发布任务结果事件。
- **协作**：由 planning、execution、review 提供场景输入、输出语义及相关规则版本；任务结果由发起业务域核验接纳。ai 不反向导入业务域实现。
- **不变量**：任务幂等、可恢复，外部调用不占用业务数据库事务；旧输入结果不得覆盖新业务版本；调用成功与业务接纳分开跟踪。

场景规则与结果含义由业务所有者维护，ai 负责调用机制与模型适配。营养数据查询及业务换算归 execution；健身限制及计划发布规则归 planning；ai 不能代用户确认事实、结论或计划。

## 5. 健身与学习的组织方式

两类业务共用目标—周—日—事实—结论协议，在各领域内部保留专属模型与规则，不新增独立健身或学习上下文。

| 领域 | 通用能力 | 健身专属 | 学习专属 |
| --- | --- | --- | --- |
| profile | 个人条件版本、可用时间 | 器材、训练基础、身体观测、饮食与适用限制 | 学习基础、资源与条件 |
| planning | 目标、草案、逐日项目、审查、发布、状态管理 | 增肌/减脂方向、训练动作与组数单位、饮食目标、睡眠安排、健身限制 | 主题、内容、时段、页/题/分钟等数量与预期成果 |
| execution | 事实身份、实际时间、修正、适用基准、自主记录 | 训练、个人摄入、睡眠、训练感受 | 实际学习内容、同单位数量、文字成果 |
| review | 来源版本、日周结论、人工补充、覆盖与确认 | 训练/饮食/恢复维度的对照与判断 | 投入及成果的对照与判断 |

使用明确类型和值对象承载专属字段，不将所有内容压入通用 JSON 实体。学习不要求身体、营养或健身方向字段；学习时长不推算掌握率，不同单位不合成统一健康分或学习分。专属策略负责内容校验，通用模型负责对象身份与版本协议。

## 6. 数据与规则的唯一所有权

| 数据或规则 | 唯一所有者 | 其他模块使用方式 |
| --- | --- | --- |
| 账户、微信/密码身份、会话、用途授权 | identity | 公开身份及授权查询，引用授权版本 |
| 数据请求与阶段进度 | identity | 各数据所有者执行处理并回执 |
| 个人条件与长期限制 | profile | 读取适用条件快照及版本 |
| 身体测量与日级身体状态 | profile | 通过事实 ID、观测时间与修订引用 |
| 分类目标及其生命周期 | planning | 引用目标身份和当时适用版本 |
| 周计划、每日项目、动作与学习任务 | planning | 读取适用修订，不跨域修改内部实体 |
| 每日饮食/睡眠目标 | planning | execution 对照基准，review 引用版本 |
| 计划审查、发布与执行保护状态 | planning | 通过公开命令核验、锁定与发布 |
| 健身发布/调整限制与规则版本 | planning | 公开评估/限制查询；身体与执行证据仍由原域保存 |
| 训练、睡眠、学习事实及训练感受 | execution | 读取公开事实快照，按事实身份去重 |
| 食物照片业务关联与分析草案 | execution | ai 仅持有本任务必需的受控图片引用 |
| 个人摄入、营养来源与份量换算 | execution | 读取已确认小计、范围、未知与覆盖 |
| 日结论、目标周复盘及确认 | review | 今日与复盘共用；planning 核验调整依据 |
| 合并后的调整草案与审查状态 | planning | review 提供来源、理由与候选差异 |
| AI 任务及调用尝试 | ai | 公开创建/取消/状态查询及结果事件 |

引用或不可变快照服务于历史追溯，不构成可独立编辑的第二份事实。各域维护自己的版本历史和处理状态；导出与删除范围覆盖本域事实、快照、派生产物及持有的对象存储关联。历史版本也按适用的数据请求处理，不能借“保留历史”绕过删除范围。

统计口径由相关领域提供：execution 提供已确认摄入小计和事实覆盖；planning 提供适用目标、可执行范围；review 负责其结论中计划实际对照的指标与判断。workspace 调用公开查询组合页面，保持各指标单位、未知和覆盖信息。

## 7. 跨域协作与一致性

| 场景 | 发起与协作 | 生效及一致性要求 |
| --- | --- | --- |
| 保存个人条件 | profile 保存版本 → planning/review 接收变更 | 相关未完成草案和审查需复核；历史按当时依据追溯 |
| 保存身体观测 | profile 保存事实 → review 更新依据；planning 核验关联限制 | 事实独立成立；新增风险对关联任务产生限制提示，限制判定不等待 AI 成功 |
| 生成/编辑/审查计划 | planning → profile/identity → ai → planning 接纳 | 手工和 AI 草案采用最新适用审查；规则阻断项须解决 |
| 确认计划 | planning 核验草案、目标、条件、授权、审查、限制和调整来源 | 原子切换明确的未来可调整范围；已开始/已有实际的基准受保护 |
| 保存训练/学习/睡眠实际 | execution → planning 基准锁定 → 保存事实与事件 | 有计划时共享本地事务；自主记录无需虚构计划；成功后异步更新 review |
| 确认摄入 | execution 核对个人份量 → planning 保护适用饮食基准 → 保存 MealRecord | 草案不入账；有当日摄入后保留当日总量基准，新总量仅未来生效 |
| 日周结论生成与确认 | review → planning/execution/profile 快照 → ai → review 接纳/人工确认 | 来源最新且覆盖明确；AI 失败保留事实和来源明确的人工判断 |
| 依据结论调整未来 | review 核验已确认来源 → planning 合并同周草案 → 审查发布 | 候选来源变化需复核；保存结论或调整草案均不自动生效 |
| 撤回/导出/删除/注销 | identity 记录请求及用途版本 → 各域处理 → 回执 | 真实阶段可恢复、可重试；旧任务不得恢复已删除或受限内容 |
