## 1. 所有权与依赖

| 领域 | 唯一拥有 | 可编译依赖的业务公开接口 | 向外提供 |
| --- | --- | --- | --- |
| identity | 账户、微信/密码身份、会话、用途授权、数据请求和阶段回执 | 无；可依赖 shared | 本人处理资格、授权版本、短事务处理栅栏、数据请求事件及回执契约 |
| profile | 条件版本、身体测量、日级身体状态 | identity | 条件、身体事实及范围版本快照 |
| planning | 目标、周草案、日项目、动作、审查、发布修订、执行保护、健身限制规则 | identity、profile、ai | 适用基准、保护命令、计划快照、健身限制评估、调整合并、来源核验端口 |
| execution | 训练、睡眠、学习、个人摄入事实及修正，食物图片关联、分析草案、营养来源换算 | identity、planning、ai | 事实、覆盖、已确认摄入小计及范围版本 |
| review | 每人每日共享结论、目标分段、目标周复盘、人工判断、确认及调整依据 | identity、profile、planning、execution、ai | 日周结论、最新已确认依据核验实现、调整候选 |
| ai | 持久任务、输入快照、尝试、租约、调用结果及接纳回执 | identity | 创建/取消/查询任务、接纳回执、结果事件 |

所有模块可依赖最小 shared；只能引用其他模块 `api` 命名接口。`workspace` 组合批量查询，不建业务表；`bootstrap` 装配接口实现。身体事实不进入 execution；训练后的单次感受不进入 profile；营养目标与餐次安排不进入 execution；营养数据库接入不进入 ai。

`planning.api.AdjustmentBasisVerifier` 的接口属于 planning，由 review 实现并在 bootstrap 装配。planning 不导入 review 的实现、实体或仓储；identity 不导入各数据所有者；ai 不导入调用方实现。来源核验实现只读源域公开接口，不再次调用计划发布或调整合并，避免运行时递归。

## 2. 基础类型及 HTTP 协议

| 项目 | 统一约定 |
| --- | --- |
| 身份 | `ActorContext` 从服务端会话取得 userId、sessionId；客户端 userId 不参与授权。后台持有服务器创建的受限 ProcessingContext，不能伪装为用户确认 |
| ID | 后端生成 UUID，数据库 `CHAR(36)`，接口字符串；客户端临时 ID 不当持久身份 |
| 版本 | 可变根 `version BIGINT NOT NULL`；不可变修订独立 revisionId / revisionNo；HTTP 编辑与确认使用 `expectedVersion`，不与修订号混用 |
| 时间 | `DATETIME(6)` 保存 UTC 时间点；HTTP 为带 Z 的 ISO 8601。`businessDate` / `weekStartDate` 为 DATE，按 Asia/Shanghai、周一计算。睡眠归起床日 |
| 数值 | DECIMAL 与明确 unit，计数用整数。缺失为 NULL 并带 known/unknown 等语义；不能将未知填 0 |
| HTTP 路由 | `/api/v1/identity/*`、`/api/v1/profile/*`、`/api/v1/planning/*`、`/api/v1/execution/*`、`/api/v1/review/*`、`/api/v1/ai/tasks/*` |
| 幂等 | 普通业务写操作带 `Idempotency-Key`，服务器映射为 requestId。唯一键 `(user_id, operation, request_id)`，同时保存规范化请求摘要与已提交结果；同键不同输入返回冲突。密码登录和本机管理员账号命令例外见第 8 节 |
| 成功 | 查询/更新 200，创建 201；异步受理 202 包含 taskId、业务对象版本与状态。受理不是业务接纳或确认 |
| 错误 | 统一 `{code,message,requestId,details}`；401 无会话，403 资格/用途受限，404 本人范围内无对象，409 版本/来源/幂等/保护范围冲突，422 业务字段或规则不满足 |

跨域公开 API 与 HTTP Controller 分开。公开契约返回不可变 ID/版本/归属/单位快照，不返回聚合或 JPA 实体。表与公开 DTO 的名称可以不同，各域需写清映射。

用途代码及账户状态以 identity 文档为所有者；消费者传入场景对应的用途集合及预期授权版本，不自行创造另一份授权枚举。人工记录与可选 AI 处理分开判断，拒绝 AI 不应使手工闭环失效。

用途代码统一为 `ACCOUNT_ACCESS`（账户/基础管理的隐含资格）、`HEALTH_DATA`（健康资料、身体、训练、睡眠本地处理）、`FOOD_IMAGE`（用户选定食物图片上传存储）、`AI_PROCESSING`（向已告知 AI 处理方发送本次最小输入）。学习手工只需 ACCOUNT_ACCESS；学习 AI 增加 AI_PROCESSING；健身额外 HEALTH_DATA；图片增加 FOOD_IMAGE。授权版本采用账户全局 `authorizationVersion`，撤回/删除/注销递增 `deletionEpoch`；重新授权不能使旧 epoch 的任务继续写入。

`ProcessingContext` 只能由服务端创建，含 userId、ownerModule、operation、resourceScope、purposes、expectedAuthorizationVersion、expectedDeletionEpoch、taskId/dataRequestId、contextKind、issuedAt、expiresAt。后台任务上下文无用户确认权限；数据请求 worker 仅可处理已受理范围，回执上下文仅可报进度。CLOSING/CLOSED 账户允许受限数据请求上下文继续清理、回执和查询进度，不允许普通业务写入。

`BACKGROUND_MAINTENANCE` 专用于 `CANCEL_TASK / REJECT_RESULT / RELEASE_LEASE / RECORD_FAILURE_METADATA / PURGE_HELD_CONTENT`：撤回后服务端按当前 epoch 重新签发给资源所有者，限 taskId/请求产物与操作白名单，在 ACTIVE/CLOSING/CLOSED 均可；不要求已撤回用途继续 GRANTED，不读/生成私人正文，不接纳结果，不执行用户确认。`lockProcessingFence` 据 contextKind 返回只含许可操作的 FencePermit，不能把旧 BACKGROUND_TASK 升级为维护或业务资格。

以下是共同方法名及最小语义。各领域在 03 文档细化完整输入、返回、错误与事务属性，不用同名方法改变语义。

数据请求类型以 identity 为准：EXPORT / DELETE / CLOSE_ACCOUNT。DELETE/CLOSE_ACCOUNT 的七方阶段为 MODULE_DATABASE / OBJECT_STORAGE / PROCESSOR / BACKUP；EXPORT 的七方为 EXPORT_SNAPSHOT / EXPORT_OBJECTS，identity 另维护 EXPORT_PACKAGE；注销还包含 identity ACCOUNT_ACCESS / ACCOUNT_FINALIZATION。阶段状态为 PENDING / RUNNING / SUCCEEDED / SKIPPED / FAILED_RETRYABLE / FAILED_FINAL / PENDING_EXTERNAL / PENDING_POLICY，SKIPPED 必须说明确无数据/不适用理由。产物以 identity 的 ArtifactDescriptor 回执登记，不用客户端任意存储键。

AI 任务精确类型及业务所有者：PLAN_GENERATION / PLAN_REVIEW 属于 planning；FOOD_ANALYSIS 属于 execution；DAILY_CONCLUSION / GOAL_WEEKLY_REVIEW / ADJUSTMENT_SUGGESTION 属于 review。createTask 返回 taskId、taskVersion、executionStatus、acceptanceStatus；普通 HTTP getTask 只返回安全进度，业务所有者使用受信上下文取得规范化候选结果。recordAcceptance 与业务结果保存共享持栅栏短事务，不单独提前宣称 ACCEPTED。

AI 上下文的 `ownerModule` 表示 origin 业务域，任务存储资源所有者仍为 ai。业务域预分配 taskId 后，在栅栏内签发 `operation=AI_CANDIDATE_PROCESSING` 封闭能力组，scope 含该 taskId 与用户选定来源范围。identity 同时检查服务端 TrustedModuleContext 和请求的具体子操作：origin 可 CREATE_TASK / READ_OWN_CANDIDATE / SAVE_OWNER_CANDIDATE / RECORD_ACCEPTANCE；固定的 ai executor 仅可 CLAIM / EXECUTE / STORE_CANDIDATE / COMPLETE / FAIL 等任务子操作。执行器不取得 origin 的业务写入或接纳回执权限，更不取得人工确认权限。所有者接纳还需自己的业务规则及最新来源核验。

任务执行/租约续期保持原 authorizationVersion / deletionEpoch / 来源范围，不能由 worker 自动升级旧授权或旧 epoch。维护上下文另由服务端按当前 epoch 签发，ownerModule=ai 且限该 taskId，仅终结状态/清理。上下文到期后继续普通处理需原业务所有者重新核验并签发受限资格；已撤回/删除的任务只能走维护路径。

计划基准保护与事实保存必须共享一个事务，公开保护命令不得使用 REQUIRES_NEW。自主事实没有基准时保持 NULL，不补造目标。共享睡眠/饮食引用多个目标时逐一返回适用引用，有冲突的基准由用户选择；事实正文仍只保存一次。

睡眠 START 允许真实 beginAt 已发生而 endAt 未知，预计起床日明确标 provisional=true，IN_PROGRESS 不进入完整睡眠指标；finish 以真实起床日修订同一事实，保留原开始保护并改变旧/新日 token。摄入移日纠正保持原事实基准，在同事务为新日期建立补充总量保护，旧槽不释放。原基准日期与纠正后日期不同需显示 baselineDateMismatch，不自动替换引用或虚构新日达标率；具体参数/表见 planning 的 03/04。

计划审查工作版支持 RULES / AI 渠道：RULES 由 planning 的版本化确定性策略完成结构、信息充分性、冲突、保护与健身限制检查，规则覆盖不足仍阻止发布，不能让用户自行声明已审查；AI 渠道额外绑定授权后的语义审查结果。AI 失败不能自动降级为通过；显式改选 RULES 须重审，禁止风险内容与未解决阻断不因切换渠道消失。生产规则及参数未落实时如实 INFORMATION_REQUIRED，不编造健康阈值。

## 4. 短事务、锁顺序与来源最新性

### 4.1 V1 用户处理栅栏

V1 采用可审查的保守并发方案：identity 的账户根行同时作为用户级处理栅栏。所有影响业务、授权、来源或删除状态的**短写事务**，首先调用 `lockProcessingFence`，由 identity 对账户根行 `SELECT ... FOR UPDATE`。同用户的短写串行；不同用户不互相阻塞。此约定是本轮新增详细设计决定，需在真实 MySQL 集成测试验证吞吐与死锁恢复，未来拆分栅栏需另记 ADR。

使用 READ COMMITTED，读取当前已提交来源；栅栏持有期间其他遵约写入不能改变来源。身份核验和来源采集、计划发布、事实保存、人工结论确认、AI 业务接纳、授权变更及实际数据清理均遵约。后台 worker 不得绕过栅栏改本域业务状态。微信首登通过微信身份唯一约束解决竞争；取得账户后遵约。密码登录事务外执行 BCrypt，短事务先锁账户再锁密码身份复核；本机重置同序锁定并撤销全部有效会话。管理员新建密码账户依赖用户名/userId 唯一约束，失败回滚，不使用公共业务幂等回执。

普通列表可短暂最终一致；标为“最新已确认”的查询、生成输入快照和确认前最终核验需在一个持栅栏的短事务读取范围版本，不能在事务外先检查再写。删除/注销请求处理中，对应范围写入由 identity 拒绝；清理小批次分别持栅栏提交，外部文件清理在事务外进行。导出不冻结一般写入：各域在短栅栏事务建立固定对象/修订选择清单及 snapshotAt，再分批读取不可变修订；组合导出说明各域采集时间，epoch 改变时取消旧导出并清理产物。

### 4.2 锁顺序与外部调用

统一顺序：账户处理栅栏 → 写请求幂等记录 → 适用全局规则选择行 FOR SHARE → profile 本域根 → planning 的 Goal / WeekPlan / 稳定项目保护行（同级按 ID 排序）→ execution 事实/草案 → review 日/周根 → ai 任务/尝试 → 持久事件登记。同用户栅栏消除主要跨域倒序竞争；各域仍按该顺序组织公开调用，禁止已锁 ai 任务再回头申请账户栅栏。

全局规则本身发布为不可变版本；`sys_planning_rule_selection` 是 V001 的无个人正文配置元数据，planning 定义规则语义，基础设施维护迁移。适用审查接纳与发布锁当前选择行 FOR SHARE 到提交；规则切换只独占该行，不再获取用户栅栏。单用户栅栏不能保护全局规则切换，不能省去此例外的锁。表结构见 planning 的 04 文档；V1 不因此新增管理端产品能力。

AI 领取、租约续期、失败完成等也是短事务；先定位 userId，再锁栅栏，再锁任务并校验 leaseToken。执行期间释放数据库锁。发起调用前重新检查资格，外部调用后重新入短事务核验；已发出的供应商请求只能尽力取消，其结果不能恢复已删除/受限内容。

微信登录兑换、AI/营养供应商、对象存储网络操作不在业务事务中等待。需要读取外部结果的流程先取得结果，再进入短事务重新校验版本保存；发起持久任务后由后台处理。数据库死锁/瞬态失败有限重试同 requestId，业务版本冲突不自动覆盖。

### 4.3 SourceReferenceSet 与范围版本

`SourceReferenceSet` 分为 `refs` 和 `scopeTokens`：refs 保存已有对象的 `(ownerModule, objectType, objectId, revisionId/version)`；scopeTokens 保存 `(ownerModule, scopeType, scopeKey, version)`。仅检查已有事实 ID 不能发现新事实、删除或新增日结论，必须比较范围版本。

各数据所有者维护本域范围版本行（可用本域 `*_source_scope` 表）：profile 条件及身体观测范围、planning 目标/日期适用计划范围、execution 用户/日/维度事实范围、review 用户/日及目标/周结论范围。首次不存在返回逻辑版本 0，第一次写入原子建立为 1；新增、纠正、删除、影响内容的确认变更在业务事务内递增，重复幂等请求不递增。旧归属日与新归属日均变化。版本行不含事实正文，隐私请求按适用范围清理。

AI 输入、计划审查、日周结论和调整依据携带相关范围 token。授权版本与 deletionEpoch 另行比较，不能用范围 token 代替授权。接纳/确认/发布最终检查在栅栏内读取当前 token；任何差异返回 SOURCE_STALE，不覆盖新内容。未发生事件消费也能拒绝过期确认。

范围 token 表示相应业务来源语义变化，不能随技术根所有写入递增。planning 的 PLAN_DAY / PLAN_GOAL_WEEK 只表示已发布适用处方/状态与真实保护，草案合并/审查/任务关联只用 draftRevisionId/输入指纹检查；执行结论不引用可变 WeekPlan.version。review 的 MANUAL 仅人工条目变更递增，确认不改变其自身人工来源；组件排除自身 DAILY/GOAL_WEEK。任务领取/进度、纯失效投影不得冒充源事实变化。写入新人工版本后先更新其token，再采集组件来源。具体表/API按所有者定义，防止“确认或合并使自己的输入立即失效”。

| 所有者 | 公开范围代码 |
| --- | --- |
| profile | CONDITIONS（COMMON / FITNESS / LEARNING）、BODY_DAY |
| planning | GOAL_SET、GOAL_STATE、PLAN_DAY、PLAN_GOAL_WEEK、全局 FITNESS_RULES |
| execution | FACT_DAY（日期\|TRAINING/LEARNING/SLEEP/MEAL）、FOOD_DRAFT |
| review | DAILY、GOAL_WEEK、MANUAL |

调用者逐字保存所有者代码/规范 scopeKey，不能另创同义枚举；userId由归属上下文单独提供。仅确实用到的来源进入集合，草案候选不作为已发生摄入来源。

## 5. 事件、任务与幂等基础设施

集成事件信封：`eventId, eventType, schemaVersion, occurredAt, ownerModule, userId, aggregateId, aggregateVersion, requestId, affectedScopes, payload`。payload 只含必要引用、状态和版本，不传播图片正文、完整身体资料或供应商秘密。

共同事件名：identity 的 `AuthorizationChanged, DataRequestCreated, AccountStatusChanged`；profile 的 `ProfileConditionsChanged, BodyObservationChanged`；planning 的 `GoalChanged, PlanDraftChanged, PlanConfirmed, PlanItemLocked`；execution 的 `ExecutionFactChanged, ExecutionFactCorrected, ExecutionFactRemoved, FoodIntakeConfirmed`；review 的 `DailyConclusionUpdated, DailyConclusionConfirmed, WeeklyReviewConfirmed, ConclusionSourceChanged`；ai 的 `AiTaskCompleted, AiTaskFailed, AiTaskCancelled`。各域可增加本域事件，需列订阅者与载荷；有重叠事件不能重复驱动同一累计。

typed 事件消费同样遵守编译依赖方向。planning 不导入 execution/review 事件类；execution/review 各自消费自身事件后，通过 planning 所有的 notifyFitnessEvidenceChanged / markAdjustmentBasisChanged 在新短事务通知投影失效。通知事务先栅栏再 planning 锁，不持 execution/review 写锁；投影通知延迟不会绕过最终来源核验。

采用 ADR-002 的单一持久事件登记机制（Spring Modulith JDBC 候选）。不并行创建另一套领域 outbox；库管理事件表 DDL 在版本锁定后由基础设施迁移负责。业务变更和发布登记同事务；消费至少一次，`sys_event_consumption` 按 `(consumer,event_id)` 去重，消费变化与去重同事务；乱序事件不能回退版本，失败可恢复重试。

库的登记写入跟随原业务事务，监听失败留下可重投记录；具体生命周期与迁移以锁定的版本为准。[Spring Modulith 事件登记说明](https://docs.spring.io/spring-modulith/reference/events.html)

`sys_command_receipt` 与 `sys_event_consumption` 是运行支撑表，不是新增业务领域，由基础设施维护并记录 user_id 以纳入隐私处理。所有者表可以保存其业务 requestId，但不能用每域不同的幂等语义替代公共协议。AI 还以 `(user_id, owner_module, task_kind, business_request_id)` 唯一，任务幂等不等于供应商恰好调用一次。

## 6. 表结构与迁移约定

MySQL 8.4 / InnoDB / utf8mb4，UUID 标识列使用 ASCII 二进制比较，枚举使用带约束的 VARCHAR，不依赖应用日志维护历史。每张业务表（含修订/子实体）显式 user_id；内部外键与唯一键同时保证父子属于同用户，跨域只保存 ID/修订引用，无跨域外键和 JPA 导航。每域 04 文档需提供逐表字段类型、可空、默认/单位、PK/FK/唯一键、查询索引及删除范围。

两个显式例外：无个人数据的全局规则选择配置没有 user_id；identity 的微信预认证兑换暂存表在尚未识别本人前 user_id 可空，只存短期受控兑换状态与摘要，识别后回填，不保存原始一次性 code 或业务正文。不能将例外扩展到身体、执行、计划或结论子表。

不能用含 NULL 的唯一键宣称“只有一个当前版本”；使用稳定头行当前指针、非空唯一槽或经说明的生成列。修订不覆盖更新，当前根用 version 乐观并发；普通误记删除以新删除修订保留审计，隐私删除则清理请求范围内正文、历史、快照、派生产物与对象关联。

锁定读取必须处于显式事务，锁保持到事务结束；READ COMMITTED 每次读取当前已提交快照，本设计的跨读取稳定性由遵约的用户栅栏补足。[MySQL 锁定读取](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)、[隔离级别](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)

MySQL 的可空唯一索引允许多个 NULL，当前身份应按稳定头行指针等方案实现。[MySQL 唯一索引说明](https://dev.mysql.com/doc/refman/8.4/en/create-index.html)

| 表 / 字段 | 类型 / 可空 | 含义 |
| --- | --- | --- |
| sys_command_receipt.id / user_id | CHAR(36) / 否 | PK、本人的归属；不建立跨域账户 FK |
| operation / request_id | VARCHAR(100) / VARCHAR(128) / 否 | 服务器固定操作代码与客户端幂等键，ASCII 二进制比较 |

约束：command receipt 唯一 `(user_id,operation,request_id)`，索引 `(user_id,created_at)`、`(expires_at)`；event consumption 唯一 `(consumer,event_id)`，索引 `(user_id,consumed_at)`。幂等记录只随成功业务事务提交；失败回滚后可用同键重试，不能永久占有 IN_PROGRESS。异步受理的重放返回原 taskId；撤回/删除后仍先检查当前访问资格，不能无条件重放旧敏感响应。

公共表、事件登记里的载荷及临时产物由 infrastructure 订阅 DataRequestCreated 并回执；业务域同时处理自己持有的所有事实、历史、输入快照和派生引用。隐私清理删除旧幂等内容后，删除 epoch 与账户/范围门禁仍阻止旧请求重建被删对象；若需要保留防重 tombstone，必须使用经保留策略批准的无正文摘要并说明期限。公共 JSON 仅是响应协议快照，不能替代领域类型化表。

## 7. 交付及共同验收

每域按既有 01～05 文档规范交付：职责与术语；带 Mermaid 核心类图的聚合/规则及状态；HTTP 与公开 API、关键请求响应、核心时序及事件；字段级表结构和事务/索引；真实 BF/UC/BR/AC 追溯与待实现测试。README 提供入口，类图源可存 diagrams。数据库结构与 API 设计是文档成果，测试章节不冒充已运行生产测试。

共同核对：同日日结论唯一且两页共享；事实和基准原子提交；部分发布不改历史；当日摄入保护总量基准；周日睡眠跨周归属；事实新增也使旧来源失效；拒绝过期 AI 与过期确认；学习不依赖健康必填；确认结论不发布计划；隐私清理不能被任务、快照或历史恢复。供应商、计算参数、保存期限等原需求待定项标明负责人/决定入口，不编造为已确认规则。

## 8. 密码认证增量及部署凭据边界

密码和微信认证均签发既有 UserSession，其他领域只接收服务端 ActorContext，不依赖用户名、密码哈希或认证渠道。密码登录不要求业务 Idempotency-Key，每次成功产生新会话；本机管理员创建/重置不是普通业务 HTTP 命令，不登记 sys_command_receipt 或新增领域事件。普通业务写入的幂等约定保持不变。

Nginx Basic Auth 只控制测试网站入口；X-EvoLoop-Session 经可信网关转为 Bearer 后仍须后端核验，不从浏览器自报 userId 授权。后端只监听本机，密码请求限速由网关承担。网关凭据与业务密码独立，均不得进入 Git、事件、普通日志或用户数据导出。

密码重置递增密码身份 version、撤销全部 ACTIVE 会话，不改变账户 version、authorizationVersion、deletionEpoch，也不扩充用途权限。密码登录不代替现有 recentVerificationProof，不新增密码敏感操作核验。详见[identity 规则](identity/02_聚合与领域规则.md)与[命令契约](identity/03_命令查询与领域事件.md)。本节按实际实现同步，其他原设计条款仍须分别验证。
