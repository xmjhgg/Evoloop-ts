## 1. 聚合与核心类图

DailyConclusion 和 GoalWeeklyReview 是两个业务聚合根，各自只管理本人一次日/目标周判断。复用 ConclusionDocument 的身份、组合修订、组件、人工版本和范围确认机制，但不把“每日 + 七天 + 周 + 计划 + 事实”加载为一个巨大聚合。AdjustmentSuggestion 是独立候选聚合，引用已确认依据和现计划值；合并后的草案属于 planning。

## 2. 修订、人工内容和范围确认

组件创建后不可修改，含独立来源、覆盖、cutoff、typed 维度指标和有类型的判断。人工条目用稳定 entryId + entryNo 保存修订，新增、编辑和移除均形成新版本；输入 AI 的 manualRevisionRefs 与组件保存的人工引用明确。AI 输出只能替换选定的机器判断，不删或覆盖人工条目。人工纠正明确标 USER_JUDGMENT，实际数量更正由 execution/profile 处理。

保存人工“补充”追加条目并建立新组件，旧机器判断标 NEEDS_UPDATE；用户可选择更新 AI 或显式填写 MANUAL_FINAL_JUDGMENT，后者在栅栏内重新采集来源、覆盖后形成可确认的 MANUAL 组件。无 AI 授权/服务失败可用该路径，不把旧 AI 判断直接标最新。只保存补充不确认。确认必须明确 explicitConfirm=true 并提交组件清单/来源指纹/覆盖摘要，不能被后台 task 自动执行。

ScopeConfirmation 绑定确认时组合修订、组件 IDs、goalIds、日期/维度、截至及缺失。最新范围确认头按 `(documentId,slotKey)` 维护；同一次可确认多个 slot。全日 ALL_AUTHORIZED 仅描述实际授权并提交的范围，不等于所有目标，无遗漏才可标完整全日确认。替换某组件时清除其确认头；复用组件保留原头，但查询仍即时验证来源。确认后根 version 递增、内容 revisionId 不变。

调整 basisRef 的 revisionId 必须为**当前组合修订**，confirmationId/version 必须为该目标组件的当前确认；确认当时组合修订可不同，但 confirmedComponentId 必须仍在当前 manifest 且来源一致。此规则允许学习局部变更而复用未涉及健康段，同时不接受老组合修订或扩张确认范围。

## 3. 内容状态与新鲜度状态

内容阶段与任务/最新性分开表示，避免“正在生成”掩盖已保存人工判断。

```mermaid
stateDiagram-v2
    [*] --> SUMMARY_ONLY: 建立事实摘要
    SUMMARY_ONLY --> AWAITING_CONFIRMATION: 接纳AI或保存人工最终判断
    SUMMARY_ONLY --> GENERATING: 申请任务
    GENERATING --> AWAITING_CONFIRMATION: 来源匹配后业务接纳
    GENERATING --> GENERATION_FAILED: AI失败或拒绝结果
    GENERATION_FAILED --> GENERATING: 明确重试最新输入
    GENERATION_FAILED --> AWAITING_CONFIRMATION: 人工最终判断
    AWAITING_CONFIRMATION --> CONFIRMED_SCOPE: 本人明确确认所选组件
    CONFIRMED_SCOPE --> NEEDS_UPDATE: 组件或底层来源变化
    AWAITING_CONFIRMATION --> NEEDS_UPDATE: 保存影响判断的补充或来源变化
    NEEDS_UPDATE --> GENERATING: 更新选定组件
    NEEDS_UPDATE --> AWAITING_CONFIRMATION: 新人工判断与来源
```

图中的 CONFIRMED_SCOPE 是所选组件状态，不强迫一根仅一个二值确认标记。查询返回各组件 contentStatus/sourceFreshness/confirmationStatus 与日根 confirmationSummary=NONE/PARTIAL/ALL_VISIBLE。FULL 最新判断需逐组件核验，健康受限时不能标 ALL_DAY。任务失败保持当前组件与人工内容，旧确认若来源仍有效可作为历史/当前范围展示；失败本身不改执行事实和计划。

## 4. 来源集和版本规则

1. refs 绑定已存在的目标/计划修订、事实修订、人工修订以及周输入日组件/确认状态；scopeTokens 对请求范围的每个日/维度返回版本，包括不存在的逻辑 0。
2. 日输入按所选组件取 planning 目标/适用日期 tokens、execution 当日相关维度 tokens、profile 必要 BODY_DAY/CONDITIONS tokens；无计划/无事实也保留对应 token。当前日还按 cutoff 明确未来排除。
3. 周输入同时读取大目标/当时周计划、每日适用基准、底层事实，以及周一至周日每个日结论组件/确认状态；缺失日仍取 review DAILY(date)=0。不能只累加日 AI 文本，不能等七天确认才生成。
4. 目标文档自身当前 token 不进入其组件 sourceSet，避免生成/确认写入后自我过期；目标根 expectedVersion 和选定组件版本独立核验。周输入包含所依赖的日 token，不包含目标周根自己的 token。
5. 生成输入、接纳、确认及“最新已确认”查询在一笔持用户栅栏的短事务采集全部来源。cutoff 限制实际发生范围，不忽略后来保存/纠正；后续新增或删除即使 occurredAt 早于 cutoff 也会让原 token 失配。
6. SourceFingerprint 对规范排序后的 refs、tokens、组件/人工输入、cutoff、coverage 和适用 schema/规则版本做 SHA-256；仅 fingerprint 相同仍需最终查来源和资格。
7. DAILY/GOAL_WEEK tokens 由内容、确认或影响判断的失效变化同事务递增；MANUAL token **只在人工条目新增/编辑/移除或相应隐私清理时递增**，确认/机器组件替换不能递增 MANUAL，避免确认使自己的人工来源立即过期。人工修改先写新 entryNo 并递增 MANUAL，再采集新组件来源。日组件/确认/人工变化影响 DAILY，进而使周来源过期；幂等重放无版本递增。
8. 事件缓存只能提示；verifier 比较原 refs 是否仍可用、当前范围 tokens、对应确认头和组件，任何不匹配拒绝。授权版本/deletionEpoch 单独核验。

## 5. 统计与解释规则

| 维度 / 场景 | 采用口径 | 禁止推断 |
| --- | --- | --- |
| 训练 | 计划项目与原基准；完成/部分/明确未执行/未登记分别计数；动作实际只取已登记 | 时长或计划组数自动代表每动作完成 |
| 摄入 | execution 已确认有效个人摄入小计；kcal/g、估算区间、未知项、餐次覆盖独立 | 漏餐为 0、只一餐推断全天不足、因估算极端补偿 |
| 睡眠 | COMPLETED 事实按真实起床日；昨夜对照当日原基准；IN_PROGRESS 标预计/provisional且不进完整睡眠值 | 今晚目标进入已发生结论；预计起床日冒充完整事实 |
| 睡眠完成跨日 | 同 factId 去重，旧/新日 tokens 改变；finish 保留原开始保护 | 后换当前计划追溯改开始基准 |
| 事实纠正移日 | 统计放到实际新归属日，保留原基准，标 baselineDateMismatch；其值可展示但 comparability=UNAVAILABLE | 原日期目标当新日基准、虚构新日达标率 |
| 身体观测 | profile 带时间/单位事实与覆盖，可描述短期变化 | 短期体重确定成效、医疗诊断 |
| 学习 | 同单位分钟/页/题各自比较，实际内容和文字成果据记录 | 投入时长等于掌握率、虚构笔记/成绩 |
| 无生效计划 | 自主事实摘要，comparison=NO_BASELINE | 虚构目标或达标率 |
| 休息/暂停/未来 | 独立状态、排除不适用分母；有效时段依据 planning | 暂停算普通缺勤、未来算漏记 |
| 日总览/周汇总 | factId/revisionId 去重；同睡眠/摄入多个 goal 引用可分段对照，总览只计一次 | 各目标分段求和重复事实，不同单位合总分 |

DECIMAL 指标必须保留 unit、knowledge=KNOWN/ESTIMATED/UNKNOWN、区间和 comparable；没有可比基准时差值 NULL。coverage 的分母规则与规则版本入快照，不自行降低历史分母。事实摘要与来源约束由确定性策略计算，AI 只能写判断/建议，不能篡改 metric/coverage。

健身建议生成或人工建议转合并前调用 planning.evaluateFitnessRestrictions 核验最新适用限制。ALLOWED/WARN/BLOCKED/INFORMATION_REQUIRED 如实展示，缺参数不能假定通过；禁止增加风险强度或极端饮食补偿内容不会因确认结论而放行。限制不阻止已发生事实保存，学习范围不受无关健康限制阻塞。

## 6. 调整建议生命周期

AdjustmentSuggestion 状态为 GENERATING → READY / FAILED / STALE；用户拒绝为 DISMISSED，全部适用差异明确送入 planning 后为 SUBMITTED。跨周只提交一组时仍 READY，返回 submittedGroups 和未提交差异，已送出 patch 不能重复送出。AI 返回 READY 仍只是候选，本域可保存 typed 字段差异和支持 statementRef。manual 建议无需 AI，但同样必须最新已确认 basis。提交时再次核验，按 `(goalId,weekStartDate(affectedDate))` 分组，用户一次显式合并一个归属周，跨周逐组提交；周日到周一使用下周唯一 WeekPlan。

每个 patch 包含 oldValue/newValue/reason/affectedDate。未开始且无实际未来项目才可候选；睡眠以真实开始保护而非归属日文字判断。planning 最终核验/三方合并，保持其他目标/日期；冲突逐项 KEEP_CURRENT/USE_PROPOSED/CUSTOM，保存不发布。已确认未来计划不会因源变更或历史修正自动改写。普通手工规划走 planning 原生入口，无复盘门槛。
