## 1. 聚合与一致性边界

| 聚合根 | 内部实体 / 值对象 | 原子变化范围 | 主要规则 |
| --- | --- | --- | --- |
| PersonalProfile | ConditionSection、ConditionRevision、AvailabilityWindow、RoutineSleepRevision/Window、ModuleResource、LongTermRestriction | 一个组件编辑命令变更一个分区；根/分区版本、新修订、当前指针、相关条件 token、幂等结果与事件一并提交；作息内容独立组件修订按 ID 复用 | BR-COM-003、008、009、015；BR-LRN-001 |
| BodyMeasurement | MeasurementRevision、MeasurementValue、ObservationTime | 同一次测量全部指标、实际时间、归属日和新修订；旧/新日 token 一并提交 | BR-COM-003、008、010、015；BR-FIT-003 |
| DailyBodyState | BodyStateRevision、FatigueLevel、MentalState、DiscomfortReport | 同一日状态新修订；日期纠正需同时更新两个日期槽和 token | BR-COM-008、011、012；BR-FIT-013 |

`DailyBodyStateSlot` 是防止同日重复当前事实的本域唯一性设施，不是用户可编辑聚合；`SourceScope` 是来源最新性设施。跨根的槽/范围版本协调由应用短事务完成，且先持 identity 用户栅栏。正常编辑只装载一个根和当前修订，不把全部测量历史加入 PersonalProfile。

## 3. 条件分区与编辑规则

1. `COMMON` 包含常规作息和通用可用时间；`FITNESS` 包含健身可用时间、训练基础、场地/器材及长期训练/饮食限制；`LEARNING` 包含学习可用时间、学习基础、书籍/课程/其他资源及长期资源/时间限制。分区内窗口是补充条件，planning 结合 COMMON 和类别分区处理交集/冲突，不由 profile 直接替人排程。
2. 命令含 PersonalProfile 的 `expectedVersion`，新建为 0；已存在根不接受 0。每个分区有自己的 version/revisionNo。更新一个分区只生成该分区修订，其他分区指针保持。根版本增加用于编辑冲突；来源引用只指向所需分区，避免健身字段变化污染学习来源。
3. 组件由 `updateMask` 指定，未指定保持当前内容，显式 null/空数组才清空选定组件。新修订保存完整合成分区及不可变作息组件 ID，不覆盖旧修订。只改 availability 复用原 routineRevisionId，禁止读取/复制健康正文；更改作息需 HEALTH_DATA 并新建 RoutineSleepRevision。学习查询不加载该组件。相同输入的幂等重试不生成新修订；新 requestId 但规范化内容无变化返回 `changed=false`，版本/token 不增加。
4. 常规窗口用上海本地分钟表示，0..1439；跨午夜 `endDayOffset=1`，否则 0；计算时长必须大于 0 且不超过 1440 分钟。特殊班次可仅填说明并把精确窗口标 UNKNOWN；不能以 00:00 默认代表未知。可用时间允许空数组，重叠/跨日窗口如实保留并提示重复，规范化后完全相同窗口不得重复保存。
5. `availabilityState=UNKNOWN/NONE/RECORDED` 区分未提供、明确无可用时间、已提供窗口。`routineState=UNKNOWN/RECORDED`；`resourcesState` 和 `restrictionsState=UNKNOWN/NONE/RECORDED`。NONE 是用户明确陈述，UNKNOWN 不能推断为无风险。知识状态与数组长度一致；RECORDED 必须有相应行/内容。
6. 健身/学习基础可空，资源按所属分区类型校验；学习条件不接受身高体重、健身方向、营养或常规睡眠字段，不以字段缺失阻断保存。饮食长期限制是条件，饮食目标计算在 planning，营养摄入在 execution。
7. 资料修订以保存时间开始成立，不开放回填 `savedAt` 或未来生效日期。`HISTORICAL_AT` 返回当时已保存的最大修订；`CURRENT_FOR_PLANNING` 取请求时当前指针。历史计划继续使用自己保存的修订引用，不能重新套用当前资料。

## 4. 身体测量规则

| 规则 | 行为 / 失败 |
| --- | --- |
| 测量事实至少包含一个数值 | 只填状态转到日身体状态命令；空值数组返回 422 EMPTY_MEASUREMENT，不推算体重 |
| 数值与单位 | V1 BODY_WEIGHT=kg、HEIGHT=cm、CIRCUMFERENCE=cm；正 DECIMAL，超出存储容量是格式错误，不是健康阈值。异常核对策略/界面提醒需产品评审，不静默修正 |
| 围度部位 | 围度带部位 code，OTHER 带非空 siteLabel；非围度 site=NONE、siteLabel 为空。一个修订不得重复相同指标/部位/标签 |
| 时间与日期 | 必填实际 observedAt；businessDate 必须等于其上海日期。保存时间服务器产生；补记过去日期合法，未来真实观测不合法（服务器时间校验，不编造医疗窗口） |
| 纠正与身份 | 用同 factId、expectedVersion 追加 CORRECT 修订；时间/数值可纠正，修正原因必填。原/新日期同时改变 scope token，历史身份不换 |
| 普通删除 | 追加 REMOVE 修订并转 REMOVED；不再作最新测量/当前事实。删除前内容保留用于普通追溯，隐私处理可以并必须清理它 |
| 同一事实复用 | 我的与今日返回同 factId/revisionId；多目标引用不复制值。不能根据相同值自动合并两个用户实际观测 |
| 删除后的编辑 | REMOVED 不接受纠正，返回 409 FACT_REMOVED；V1 无恢复命令，需要重新记录新的真实事实，不能由旧任务恢复 |

没有全域“每人每日只能一次体重”的限制：同日可以多次测量，latest 只是带时间的查询投影。日状态的唯一槽规则不用于身体测量。

## 5. 日身体状态与风险证据

日状态保存一组当日用户报告，而非一天多条训练后感受。`fatigue=UNKNOWN/NONE/MILD/MODERATE/STRONG`；`mental=UNKNOWN/LOW/NORMAL/GOOD`；`discomfortState=UNKNOWN/NONE/RECORDED`，RECORDED 时 `intensity=UNKNOWN/MILD/OBVIOUS` 且 description 非空。分类是用户自述的候选技术枚举，正式文案需评审；不映射诊断或医疗数值。至少一个状态维度已知；全部 UNKNOWN 返回 422 EMPTY_BODY_STATE。

同人同上海日期最多一个 ACTIVE DailyBodyState。创建先锁日期槽，已占槽返回 409 BODY_STATE_DAY_OCCUPIED 并返回本人已有 factId/version，客户端进入纠正流程。正常纠正追加修订；修改 observedAt 时随之校验/改变 businessDate，先按日期排序锁原/新槽。目标槽有其他当前 factId 时原子失败，原事实与两个 token 均保持；不得覆盖、拼接或静默合并。

用户自述 OBVIOUS 是明显不适证据，不是 profile 的医学判断。`BodyObservationChanged` 提供 factId/最新 revisionId/影响日期，planning 的公开限制查询直接读取当前状态与长期限制，以 BR-FIT-013 做关联限制；AI 不参与是否继续鼓励风险任务的前置判断。如实记录实际事实不因风险被拒绝，学习无关功能不被健身限制阻断。

## 6. 状态与版本

```mermaid
stateDiagram-v2
    [*] --> NotProvided
    NotProvided --> Current: 保存首个条件分区修订
    Current --> Current: 合法组件修改 / 新修订
    Current --> Current: 重复请求或无变化 / 无新版本
    Current --> [*]: 隐私清理该分区及历史
```

```mermaid
stateDiagram-v2
    [*] --> Active: 登记或补记 / version 1
    Active --> Active: 纠正 / revisionNo 和 version 增加
    Active --> Removed: 普通误记删除 / REMOVE 修订
    Removed --> Removed: 相同请求重放 / 不新增
    Active --> [*]: 隐私物理清理
    Removed --> [*]: 隐私物理清理
```

条件没有“用户确认后才生效”的状态；保存就成为当前条件。事实也无 AI 待确认状态。任何 expectedVersion 不匹配返回 409 VERSION_CONFLICT，附 currentVersion；业务冲突不能自动重试覆盖。短事务失败全部回滚根、修订、槽、token、幂等结果及事件登记。

## 7. SourceReferenceSet

| scopeType | scopeKey | 变化时递增 |
| --- | --- | --- |
| CONDITIONS | COMMON / FITNESS / LEARNING | 对应分区内容实际变化、范围内隐私清理 |
| BODY_DAY | `yyyy-MM-dd` | 该日任一身体测量/日状态新增、纠正、移出/移入、普通删除、范围内隐私清理 |

范围 token 故意包含整个日的身体证据；更细的指标版本不是 V1 必需。首次不存在返回逻辑 0；首次变化以原子插入建立 1。dateRange 查询必须返回每个请求日的 token，包括无事实日；事实 refs 查询同时返回当前归属日及调用方提供的原归属日 token，避免只查现有 ID 漏检新增或日期变化。消费方若只持有 refs，不能声称来源范围最新。

范围版本、root.version、revisionNo 的语义不同：root.version 管编辑，revisionId 引用内容，scopeToken 管集合变化。授权版本与 deletionEpoch 由 identity 单独核验。隐私请求若清掉 token 行，旧 token 可能再从 0/1 开始，因此消费者必须先核对 deletionEpoch；不能仅凭相同 token 接纳删除前任务。

## 8. 隐私清理的修订例外

不可变修订指正常业务编辑只能追加；隐私请求不是借旧修订保存被删除正文的理由。只删除常规作息组件时，建立新的 COMMON 当前修订保留已授权可用时间、清作息指针；历次 COMMON 修订的作息引用置空、标记 `privacyRedactedAt`，物理清掉匹配作息组件及其导出快照/选择关联。历史查询明确 HEALTH_COMPONENT_ERASED，不能假称原健康内容仍完整；下游的旧完整来源由 epoch/token 拒绝。原可用时间可按请求范围保留，清理不从被删作息推算任何新值。
