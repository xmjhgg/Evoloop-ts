## 1. 仓储与映射

| 仓储 / 查询端口 | 表 | 加载与保存 |
| --- | --- | --- |
| PersonalProfileRepository | personal_profile、condition_section、condition_revision 及条件修订子表 | 编辑锁根，加载相关分区当前修订；新修订完整保存子实体，其他分区指针保持 |
| BodyMeasurementRepository | body_measurement、measurement_revision、measurement_value_revision | 按 userId/factId 取根+当前修订；追加修订、更新根读投影，不加载全部历史 |
| DailyBodyStateRepository | daily_body_state、body_state_revision、daily_body_state_slot | 根+当前修订；日槽唯一由本域设施协调，移日按日期排序锁槽 |
| ProfileSourceScopeRepository | source_scope | 批量取范围；不存在逻辑 0，写时原子建立/递增 |
| ProfileSnapshotQuery | 条件/事实修订投影 | 批量组装公开 DTO，历史以明确 revisionId 或 savedAt 截止查询；不跨域 SQL |
| ProfileDataRequestWorkRepository | data_request_work、data_request_selection | 本域可恢复处理进度与稳定导出选择清单；identity 仍拥有总请求与公开阶段状态 |

下文完整表名以 `prf_` 开头。领域类不继承 JPA 类型；映射实体只在 `infrastructure.persistence`，UUID/单位/知识状态先在 domain 校验再转表。根里的当前时间/日期是由当前修订维护的读投影，没有独立编辑入口。

## 2. 全表约定与内部外键

所有 UUID 列为 `CHAR(36) CHARACTER SET ascii COLLATE ascii_bin`；下表简写 `CHAR(36)`。所有业务表及修订子表显式 `user_id CHAR(36) NOT NULL`，无默认值；user_id 是 identity 引用，不建跨域 FK。时间点 `DATETIME(6)` 保存 UTC；上海业务日期 `DATE`。BIGINT 版本正值、只由服务器增加；不使用 MySQL ENUM，VARCHAR 枚举加 CHECK。未标默认的字段无默认值；主键 UUID 由应用生成。JSON 仅用于受验证的数据请求技术范围，不用于替代条件或身体模型。

所有根/修订有对应 `(user_id,id)` UNIQUE，为子表同用户 FK 提供候选键。FK 采用 RESTRICT/NO ACTION，由仓储明确顺序清理，避免级联漏掉事件/请求回执。当前修订指针使用 `(user_id,root_id,current_revision_id)` 指向 `(user_id,root_id,id)`；同时约束同用户及同一个根。创建循环引用时，根先写 current_revision_id=NULL，写修订后设置指针，同事务提交前校验完整；正常有内容的根不允许以 NULL 指针提交。此 NULL 用于初始化/物理清理顺序，不用含 NULL 唯一键声称当前唯一。

条件分区头 `(user_id,profile_id,section_type)` 非空唯一；日期槽的 `(user_id,business_date)` 非空主键；因此当前身份唯一可由数据库证明。当前修订只有头行的一个指针，不通过 `is_current` 多行标志维护。

### 5.3 `prf_daily_body_state_slot`

| 字段 | MySQL 类型 | NULL | 默认 / 含义 |
| --- | --- | --- | --- |
| user_id | CHAR(36) | 否 | PK 第一列 |
| business_date | DATE | 否 | PK 第二列，上海日期 |
| current_body_state_id | CHAR(36) | 是 | 当前 ACTIVE 事实；空槽为 NULL |
| updated_at | DATETIME(6) | 否 | UTC |

PK `(user_id,business_date)` 保证一日仅一个槽。UNIQUE `(user_id,current_body_state_id)` 禁止同一非空事实占多槽；允许多个空槽，是明确空指针语义，不以此证明日唯一。FK `(user_id,current_body_state_id,business_date)` → daily_body_state `(user_id,id,current_business_date)`；另设同列索引。应用确保被引用根 ACTIVE。

日期纠正顺序：持栅栏 → 锁事实 → 按日期排序锁/建立两个槽 → 目标空槽检查 → 原槽指针清 NULL → 追加修订并改根日期/指针 → 新槽设 factId → 更新两个 token → 提交。MySQL FK 即时校验，不能先改被槽引用的根日期；失败全部回滚。普通删除先清槽再转根 REMOVED；隐私清理先清/删除槽，再清根指针、修订和根。槽不含身体正文，但日期/ID仍属于隐私范围。

## 7. 提交、查询与并发

保存新根先写头行空指针，再写 revision 与子表，最后设 current_revision_id。修订序号在持栅栏和根锁后从当前+1取得，唯一键防止实现绕过时重复。根使用 `UPDATE ... WHERE user_id=? AND id=? AND version=?` 断言影响 1 行；不能只先读 version 后无条件写。版本/内容一致由同事务及仓储提交前检查保证。

最新指标 SQL 只连根当前修订和值，过滤 ACTIVE 和观测截止，以实际观测时间 DESC、factId DESC 决定顺序。删除最新后自然回退到前一有效观测；补记旧日期不覆写新日期。日状态通过日期槽定位再查当前修订。历史读以修订 ID 或 `(saved_at,revision_no)` 排序；普通查询不会把 REMOVE 修订视为身体数值。

任何改变条件/观测/source token 的后台流程也先栅栏。跨域事务不使用 REQUIRES_NEW；profile 数据写不调用 planning。公共 `sys_command_receipt`、`sys_event_consumption`、单一持久事件登记由 V001 基础设施维护，本域不另建 outbox、幂等表或授权表。

## 8. 导出、普通删除与隐私清理

| 动作 | 本域范围 / 处理 |
| --- | --- |
| 普通误记删除 | 仅当前根 REMOVED/槽释放，追加无正文 REMOVE 修订；旧正文可用于普通历史，导出可依用户范围包含删除状态与修正链 |
| 导出 | 按 identity 选择范围，包含选定分区修订、观测事实/时间/单位、修正链及 refs/token 说明；空范围明确返回空，不附健康无关资料。短栅栏建立 data_request_selection，释放后分批读取确定修订；导出不冻结普通写入，不能在持续变化的当前指针分页上声称同一快照 |
| 观测隐私删除 | 对选定 factId 或任一修订命中所选日期的事实，清理该事实全部历史、值子表、当前头、日槽关联及本域持有的导出片段；跨日纠正链一起清理，影响范围须在 identity 确认前展示 |
| 条件分区隐私删除 | 清理选定分区所有修订、可用时间/作息/资源/限制及专属表；其他分区保留；根 version 与所选 token 改变，空根可清理。删除范围不是“只清当前正文” |
| 仅作息组件隐私删除 | COMMON 生成新当前修订保留可用时间、routineRevisionId 清空；历次 COMMON 的作息指针清空、routineState=UNKNOWN、privacyRedactedAt 标记；全部匹配作息组件正文、导出清单/片段清理。历史显示 HEALTH_COMPONENT_ERASED，正常不可变规则对隐私删节有明确例外 |
| 注销/全部隐私删除 | 本人全部上述业务表、范围版本、工作选择器及本域导出关联；公共设施中的回执/事件含本人引用由其所有者参与清理 |

导出外部对象写入不占数据库事务；最终取得产物前持栅栏核验当前资格/请求状态/epoch，变化则销毁不再允许提供的片段并报告真实失败/清理中。导出格式、下载有效期与备份处理时限依 TBD-003，未定前不可承诺时长。

隐私清理按批次持栅栏，采用稳定 objectId 顺序，stage/cursor/清理动作同事务提交；同请求重试不复活对象，已经不存在的对象视本阶段已清理。清理顺序为解除槽与当前指针 → 子表 → 修订 → 根 → 持有选定对象的选择清单/工作产物关联。删除/注销请求范围内普通写入由 identity 拒绝。更新影响 token 或由 identity epoch 表明已清理；对未清源域及派生域发引用/影响范围通知。当前处理 work 清理 scope_json、captured_source_tokens、游标及产物键后，只将必要无正文回执交 identity；可按请求范围删除选择清单/工作行，不能以“审计”永久保留被请求删除的身体描述/历史/快照。

`scope_json NOT NULL` 清理时置为经验证的空对象或删除工作行；不是写SQL NULL。仅作息清理先解除所有 condition_revision 的 routine引用并打删节标记，后删组件；全部分区清理同理先解引用，删除PersonalProfile根前先清其条件分区及独立作息组件。删节是隐私请求的必要例外，不能作为普通编辑直接改历史的通道；处理上下文限定identity签发的本域数据请求操作，最小回执不带身体正文。

planning/review/ai 持有的不可变输入快照由各所有者清理，profile 回执不能替它们宣称完成。profile 没有供应商接入，不伪造第三方清理证明；基础设施备份/对象存储阶段未完成时上报未完成项，identity 总请求继续处理中。普通条件删除、事实隐私删除不静默改已确认未来计划，相关来源和展示按实际清理状态处理。
