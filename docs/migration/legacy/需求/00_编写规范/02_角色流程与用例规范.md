# 角色、流程与用例编写规范

| 版本 | 日期 | 状态 |
| --- | --- | --- |
| v0.2 | 2026-10-10 | 草稿 |

来源：产品规划 V1 v0.3、前端布局设计v0.3及本轮用户要求。维护责任人待指定。

## 1. 角色怎么写

业务角色根据使用目标、责任和权限定义。健身/学习是个人用户的模块分类，增肌/减脂是健身目标的方向，登录前后是使用状态，均不另建业务角色。

每个角色写清：业务目标、负责的动作、可查阅/修改/确认的数据、不允许的动作，以及主要流程。AI、微信登录及营养数据资源在协作参与方中说明；系统内部自动动作在流程步骤中说明，不为了凑角色新增管理端或权限。

## 2. 流程怎么写

业务流程描述一个端到端目标，例如“完成当天执行登记”，可包含多个用例。每份流程必须包含触发、参与方、前置条件、步骤、替代/异常分支、结束结果、状态变化和关联用例。

步骤表使用“步骤编号｜执行方｜动作与结果｜关联用例/规则”。关键流程建议配 Mermaid 图，至少能区分用户输入、AI 建议、系统校验、人工确认和生效/入账。

一个流程只说明业务先后与分工。字段校验和详细按钮分支在对应 UC 中维护。首次生成与下周生成若使用同一能力，复用用例，并写明场景差异。

## 3. 用例怎么拆

用例按可独立验收的用户目标拆分，例如“获取食物分析结果”和“确认实际摄入”分别有不同结束状态，应独立成用例。

单个点击、后端接口、AI 提示词、表字段或算法步骤不自动构成用例。不同角色或流程使用相同行为与规则时复用正文；触发、权限、结果存在实质差异时再拆分。

## 4. 每份用例的必写内容

| 内容 | 必须回答的问题 |
| --- | --- |
| 基本信息 | 编号、版本、状态、角色、流程、F 来源、优先级、责任人、更新日期 |
| 用户目标与边界 | 用户想完成什么？本用例在哪一步结束？ |
| 触发与前置 | 如何进入？需要哪些授权、已有数据或状态？ |
| 输入与字段 | 字段含义、单位、必填条件、来源、允许未知与可编辑范围 |
| 主成功流程 | 用户做什么，系统响应什么，什么时候调用 AI，什么时候需要确认？ |
| 替代与异常 | 无计划、漏记、拒绝授权、失败、超时、重复、过期、冲突如何处理？ |
| 输出与状态 | 生成/修改什么对象？是否生效、入账、保留草案或失效？ |
| 规则与权限 | 引用哪些 BR？哪些动作仅允许数据本人执行？ |
| 验收标准 | 给定条件、执行动作、应出现的可观察结果 |
| 变更与待决策 | 新版本改变什么？哪些点尚未决定？ |

没有影响的项目填写“不适用并说明原因”，不能默默省略。已评审用例中不得遗留影响实现或验收的待决策项。

## 5. AI 场景的额外要求

- 区分用户事实、数据库/标签数值、AI 估算与建议，写清输入依据和未知项。
- AI 任务必须描述等待、失败、重试、退出返回、结果过期与重复请求。
- 写清结果先进入哪种草案状态，谁可以修改，哪些操作才导致生效或入账。
- AI 输出可采用字段表或业务样例，不把某段固定回答当成唯一正确输出。
- 可核对的汇总、单位、版本与权限由系统规则保证；健康规则、供应商、方法等未决项明确登记。
- 要求引用来源与版本，不在需求正文中内嵌模型密钥、具体数据库表结构或接口实现。

## 6. 验收条目与设计就绪

每条验收采用“给定……当……则……”，编号为 UC-模块-序号-AC-序号。用例 AC 可关联产品级 A-*；产品级验收与用例级验收各自保留。

正文完成表示章节写齐，不代表规则已确认。进入开发拆解前应能够确认：主流程、权限、关键字段、边界/异常、状态结果、验收及关联规则均明确；未解决的实质冲突登记为待决策。

评审意见应指出具体编号、影响和结论，避免只写“基本没问题”。开发和验收随后单独记录，不能把示例或追溯关系标成已实现。

通用用例定义跨模块的对象和状态协议，模块用例只展开专属字段与动作，并明确复用关系。四页视图不复制目标、事实或结论；保存事实、确认结论和确认计划要分别定义。
