# 迭代与变更规范

| 版本 | 日期 | 状态 |

来源：产品规划 V1 v0.3、前端布局设计v0.3及本轮用户要求。维护责任人待指定。

## 1. 当前正文与迭代记录

角色、流程、用例和公共规则维护当前完整需求。迭代说明仅登记本轮新增、修改、废止的内容和边界，不能复制一套正文后分别修改。

产品版本、文档版本与运行时计划版本分别记录。例如产品目标 V1、产品规划文档 v0.3、某用例文档 v0.1，不表示用户计划的第几次变更。

## 2. 修改步骤

1. 将需求变化登记为 CHG，记明来源、原因、变化前后与适用版本。
2. 分析影响：角色/权限 → 流程 → 用例 → 公共规则 → 数据口径 → 产品范围与验收。
3. 修改受影响正文，更新文档版本、变更记录、清单、追溯矩阵及本轮迭代说明。
4. 检查引用完整、编号稳定、旧需求与新需求无矛盾，记录待决策或评审结论。
5. 在实际实施后记录实现与验收证据，再更新交付状态。

同一用户请求可合并为一份 CHG；只改文字表达且不改变行为时，注明“编辑性修改”，仍更新受影响文件的版本记录。

## 3. 版本、冻结与历史

草稿初版 v0.1；后续每次形成可评审的改动递增文档版本。产品规划现有 v0.3 保留自己的版本链。

正式基线仅在相关范围获得确认后建立，以“BL-日期-序号”命名：包含快照或可恢复的仓库修订、文档版本清单、范围、评审结论及未纳入项。当前项目尚无正式基线，不虚构提交号。

基线不可回写。新版本在当前正文继续维护，通过 CHG 说明差异；废止项保留编号、历史、原因与替代关系。正式基线与旧文档版本不能用文件修改时间判断优先级。

## 4. 各项状态分开记录

| 维度 | 建议状态 |
| --- | --- |
| 文档 | 待编写 / 草稿 / 待评审 / 已评审 / 已废止 |
| 变更 | 已记录 / 影响分析中 / 已同步正文 / 已评审 / 已撤销 |
| 实现 | 未开始 / 进行中 / 已实现 |
| 验收 | 未执行 / 执行中 / 通过 / 未通过 |

用户直接确认的需求和当前会话中的授权作为来源记录，不重复发起同一确认。文档编写和已授权的可逆更新可持续进行；待评审状态只是实际进度描述。

出现文档冲突时登记冲突编号、来源、影响和待确定结论，不能凭“哪个文件更新更晚”自行覆盖已经明确的用户要求。

## 5. 变更完成检查

- 是否明确新增、修改、废止及“不受影响”的范围？
- 是否保留稳定编号，避免创建同名重复用例？
- 是否同步角色/流程/用例/规则及 F、A、AC 关联？
- 是否更新实际受影响的状态、版本与导航，保留已有人工修改？
- 是否区分“需求已写清”与“已开发、已验证”？
- 是否登记尚未决定的输入口径、冲突处理和验收条件？

## 6. 后续模块

学习已登记LRN并复用ROLE-001；新增工作/财务等模块时先明确业务目标，再建立流程和用例。可复用登录、授权、数据管理及共通确认原则，不能直接复制健身的热量、睡眠或食物记录字段。

通用用例定义跨模块的对象和状态协议，模块用例只展开专属字段与动作，并明确复用关系。四页视图不复制目标、事实或结论；保存事实、确认结论和确认计划要分别定义。
